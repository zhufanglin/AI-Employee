## 二、接口表

前缀 `/api`，全局 `JwtAuthGuard`；所有操作以 `req.user.id` 为隔离边界，越权按不存在处理（404）。

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| GET | `/memory/list` | query: `query?`、`kind?`（note/fact/preference/lesson）、`limit?`（1–50，默认 20，越界钳制）、`cursor?` | `{ items[], nextCursor, total }` |
| GET | `/memory/stats` | — | `{ total, byKind:{note,fact,preference,lesson}, last7d, topTags:[{tag,count}] }` |
| DELETE | `/memory/:id` | path id | `{ success:true, id }`；不存在/他人 404「记忆不存在或不属于你」 |
| POST | `/memory/merge` | `{ keepId, dropId }` | `{ id, content, tags[], hitCount, mergedFrom[], usedLlm }` |
| POST | `/memory/dedupe` | `{ mode?: "report"|"apply", limit?: 1–60 }` | 能力层 `memory_dedupe` 的 data 原样返回 |

细节：

- **list 排序/分页**：`orderBy: [{createdAt:"desc"},{id:"desc"}]`，多取 1 条判断 `nextCursor`。cursor 先按 `{id:cursor,userId}` 找锚点；锚点不存在（被删/伪造/他人 id）时按第一页处理，不报错。
- **list 查询**：`query` 对 `title/content/tags` 做 `contains`（OR）；`total` 用同一筛选条件（不含 cursor）`count`。
- **tags**：库里是逗号分隔字符串（可能 null），出参统一 `string[]`（trim、过滤空串）。
- **stats**：`groupBy(kind)` + `count` + 拉 `tags` 列在 JS 里聚合；`byKind` 永远补齐四类（缺省 0）；`topTags` 按次数降序、同次数按标签名排序、最多 8 个；`last7d` 以 `createdAt >= now-7d` 计。
- **dedupe**：接口层默认 `mode=apply`、`limit=30`（能力层自身默认是 report，故接口必须显式传），再委托 `CapabilityService.run({id:userId}, "memory_dedupe", {mode, limit})`；能力返回 `success:false` 时转成 400 + 后端原文（如「记忆清理需要语义模型…」），前端可直接展示。

## 三、合并策略（merge）

1. 校验：`keepId`/`dropId` 必填且不同（同 id → 400「keepId 与 dropId 不能相同」）；两条都按 `{id,userId}` 查询，任一不存在 → 404「记忆不存在或不属于你」。
2. **保留更早的**：比较 `createdAt`，无论调用方怎么传，最终保留时间更早那条；时间相同时以传入的 `keepId` 为准。返回值 `id` 是实际保留的 id。
3. 正文：调用 `judgeMemory(providers, keep.content, [{id:drop.id,title:drop.title,text:drop.content}])`，**仅当** `relation === "merge"` 且 `merged` 非空时采用模型结果（`usedLlm=true`）；否则退化 `keep.content + "\n" + drop.content`，截 4000 字。语义模型异常不影响手动合并（内部已 catch，最终拼接）。
4. 标签：保序并集去重，逗号拼接总长 ≤512（超出的尾部标签直接丢弃）；title 用 `keep.title || drop.title`；`hitCount = keep + drop`。
5. 落库：`$transaction(async tx => { tx.agentMemory.update(keep); tx.agentMemory.delete(drop); })`，两步同一事务。
6. 返回：`{ id, content, tags:[], hitCount, mergedFrom:[drop.id], usedLlm }`。

## 五、踩坑 / 注意

- **不要用 `PrismaService.delete` 直接删**：先 `findFirst({id,userId})` 判 404，再用 `deleteMany({id,userId})`，保证「他人 id」永远不泄露存在性；merge 的事务里才用 `delete({id})`（已在事务前校验过归属）。
- **Prisma 的 `cursor` 关键词不能替代 keyset**：本接口按契约手写 `createdAt + id` 边界条件，避免同毫秒多条时跳条/重复。
- **接口 dedupe 默认 apply 与能力默认 report 不一致**：能力层 `memory_dedupe` 不传 mode 默认 report（保护数据），REST 契约要求默认 apply，因此 service 必须显式补 `mode`，否则前端「执行」会变成只出报告。
- **MySQL LIKE 大小写**：`contains` 在 MySQL 默认排序规则下大小写不敏感，查询行为与能力层 memory_search 一致，无需额外 `mode:"insensitive"`。
- **生产验证的 list 定位**：merge 若走 LLM，合并正文可能改写掉测试标记字符串，故验证时标题保留 `keep.title`（带标记），用 `query=标记` 仍能命中；不要只靠正文断言。
- 生产 60 秒短信频控：脚本拿不到 `devCode` 时 sleep 62s 重试，最多 3 次；若生产不返回 devCode 则验收会 abort，需要 lead 手动提供验证码方案。
- 未改 schema、未新增依赖；`AgentMemory` 的现有索引 `[userId, createdAt]` / `[userId, kind]` 足够支撑本组查询，暂不需要迁移。
