# 媒体限额口径（最终：只保留全局上限）

> 结论（2026-11-06 用户最终决定）：**体验版只保留三项全局上限，不加按任务类型的次数上限**。
> 期间曾实现过「文生图 2 次/日、图生视频 1 次/日」的分类上限，已按用户决定**撤回**（`media.service.ts` 与 `.env.example` 由 codex 撤回，本地/生产 `.env` 与冒烟脚本由 dsh-lead 清理）。本文件保留决策记录，避免以后重复讨论。

## 生效上限（`packages/server/src/media/media.service.ts` 的 `submit()`）
| env | 默认 | 判定依据 |
| --- | --- | --- |
| `MEDIA_DAILY_LIMIT` | 50 | 当日该用户的媒体任务总数（所有类型合计） |
| `MEDIA_DAILY_SECONDS_LIMIT` | 600 | 当日累计 `inputSeconds` |
| `MEDIA_CONCURRENT_LIMIT` | 3 | 进行中（QUEUED/RUNNING/SUBMITTING/REVIEW）任务数 |

日界按 UTC+8 计算：`start = floor((now + 8h) / 1d) * 1d - 8h`；三项检查与预扣在同一事务内、`SELECT ... FOR UPDATE` 之后执行，因此被拒时**不会产生扣费流水**。

错误文案：
- `今日媒体生成次数已达上限（50 次）`
- `今日媒体生成时长已达上限（600 秒）`
- `同时进行的媒体任务已达上限（3 个）`

## 为什么不做分类上限
1. 分类上限会直接改变客户可用额度（同一账号能出的图/视频数变少），属于**产品口径**而非工程实现，需要定价与套餐一起定，用户已明确「定价后面再说」。
2. 加上分类上限后 T-33 的成本护栏冒烟失败，说明两套口径会打架；等定价定稿后按套餐统一收敛更干净。
3. 现有全局上限 + 余额校验（`算力不足，请充值`）+ 余额封顶（超额不追扣）已经能兜住内测期的成本风险。

## 内测期若要控成本（不改代码）
- 直接调小 `MEDIA_DAILY_LIMIT`（例如 5）即可整体收紧；
- 上游侧成本仍可在后台 `媒体消耗` 视图与 `/media/usage/summary` 观察（含 `consumeCoins` 汇总与 `costStatus` 待核算标记）。
