## 2. 设计要点（为什么这么写）

- **只从 `.env` 取连接参数**：脚本解析 `DATABASE_URL`，只用 user/password/host/port/db 五个字段，**密码只通过 `docker exec -e MYSQL_PWD=...` 传给容器内的 mysqldump**，绝不进命令行参数以外的地方、不进日志（日志里统一显示 `***`）。`%40` 这类 URL 转义由脚本内的 urldecode 还原。
- **`--single-transaction --quick --routines --events --databases <db>`**：业务表（InnoDB）不锁表、不缓存整表；带上存储过程/事件，避免恢复后定时任务消失。
- **额外 `--default-character-set=utf8mb4` 与 `--no-tablespaces`**：前者防止中文/emoji 变问号；后者避免低权限账号因 PROCESS 权限报 `Access denied ... PROCESS`（MySQL 5.7+/8.0 常见）。
- **先写 `.partial`，`gzip -t` 校验后再改名**：中途失败/断电不会留下一个「看起来正常」的半个备份；失败时 EXIT trap 会删掉 `.partial`。
- **`.sha256` 用相对文件名生成**：这样 `cd /opt/fcmediaagent/backups/mysql && sha256sum -c fcmediaagent-xxx.sql.gz.sha256` 直接可用，不受目录搬迁影响。
- **保留 14 天**：`RETENTION_DAYS` 环境变量（或 systemd 单元里的 `Environment=`）可覆盖；清理只删 `fcmediaagent-*.sql.gz` 及其 `.sha256`，不碰目录里别的东西。
- **`--oss` 失败只告警**：本地备份成功即视为成功（退出码 0），异地失败会给出一行 `警告：OSS 上传失败...`，避免 OSS 抖动导致 systemd 天天报 failed。
- **恢复默认演练**：默认只建临时库 `fcm_restore_<时间戳>`，打印每张表 `COUNT(*)`，然后问你要不要删临时库；只有显式 `--apply` 才动生产库，且必须先自动做一次即时备份 + 手动输入大写 `YES`。
- **恢复全程不落盘解压**：`gunzip -c | docker exec -i ... mysql`，大库恢复不需要额外磁盘空间。

## 3. 部署步骤（在生产机执行）

```bash
# 0) 目录准备（本波新建，幂等）
mkdir -p /opt/fcmediaagent/ops /opt/fcmediaagent/backups/mysql /opt/fcmediaagent/backups/logs /opt/fcmediaagent/logs

# 1) 上传三个脚本（从本仓库 scp 或 rsync 到 /opt/fcmediaagent/ops/）
#    backup-prod.sh restore-prod.sh oss-upload.mjs
chmod 0755 /opt/fcmediaagent/ops/backup-prod.sh /opt/fcmediaagent/ops/restore-prod.sh
chmod 0644 /opt/fcmediaagent/ops/oss-upload.mjs

# 2) 先干跑确认连接串解析正确（不会执行 docker、不写文件）
/opt/fcmediaagent/ops/backup-prod.sh --dry-run

# 3) 真实跑一次（第一次务必人肉看输出）
/opt/fcmediaagent/ops/backup-prod.sh

# 4) 装 systemd 单元
install -m 0644 fcmediaagent-backup.service /etc/systemd/system/
install -m 0644 fcmediaagent-backup.timer   /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now fcmediaagent-backup.timer
systemctl list-timers fcmediaagent-backup.timer --no-pager

# 5) 手动验证一次单元本身能跑通（不用等到 03:30）
systemctl start fcmediaagent-backup.service
systemctl status fcmediaagent-backup.service --no-pager -l
journalctl -u fcmediaagent-backup.service -n 50 --no-pager
```

验收：`/opt/fcmediaagent/backups/mysql/` 里出现 `.sql.gz` 与 `.sql.gz.sha256`，且 `sha256sum -c` 通过；`systemctl list-timers` 里下一次触发是次日 03:30。

## 4. 日常操作

```bash
# 手动备份一次
/opt/fcmediaagent/ops/backup-prod.sh

# 连同 OSS 异地备份
/opt/fcmediaagent/ops/backup-prod.sh --oss
# 或：OSS_UPLOAD=1 /opt/fcmediaagent/ops/backup-prod.sh

# 改保留天数（临时）
RETENTION_DAYS=30 /opt/fcmediaagent/ops/backup-prod.sh
# 永久改：编辑 /etc/systemd/system/fcmediaagent-backup.service 里的 Environment=RETENTION_DAYS=74，然后 daemon-reload

# 看一眼现有备份
ls -lh /opt/fcmediaagent/backups/mysql/

# 校验最新备份完整性（冒烟）
cd /opt/fcmediaagent/backups/mysql && sha256sum -c $(ls -t *.sha256 | head -1)

# 备份日志
tail -50 /opt/fcmediaagent/logs/backup.log
```

OSS 上传单独用：

```bash
/opt/node/bin/node /opt/fcmediaagent/ops/oss-upload.mjs --dry-run /opt/fcmediaagent/backups/mysql/fcmediaagent-20261112-033000.sql.gz
/opt/node/bin/node /opt/fcmediaagent/ops/oss-upload.mjs /opt/fcmediaagent/backups/mysql/fcmediaagent-20261112-033000.sql.gz
```

上传后的对象 key：`backups/mysql/<文件名>`，桶由 `.env` 的 `OSS_BUCKET` 决定（当前 `zhongke001`）。

## 5. 恢复

### 5.1 演练（默认，不动生产库）

```bash
/opt/fcmediaagent/ops/restore-prod.sh /opt/fcmediaagent/backups/mysql/fcmediaagent-20261112-033000.sql.gz
```

它做四件事：

1. 从 dump 头部识别原库名，并改写 `CREATE DATABASE` / `USE` 到临时库 `fcm_restore_<YYYYmmddHHMMSS>`（`--to-db NAME` 可自定名字）；
2. `gunzip -c | docker exec -i fcm-mysql mysql` 导入临时库；
3. 打印**每张表的精确 `COUNT(*)`**（一个 `UNION ALL` 查询，`mysql -t` 表格输出）；
4. 询问是否 `DROP DATABASE fcm_restore_...`（默认不删，答 `y` 才删；失败时保留现场并给出 DROP 命令）。

演练通过（表数量、行数量级与预期一致）才考虑 `--apply`。

### 5.2 覆盖生产库（灾难恢复）

```bash
# 1) 先停写：api 和 worker 都停，避免恢复期间有新写入
systemctl stop fcmediaagent-api fcmediaagent-worker

# 2) 建议先在 5.1 演练通过

# 3) 覆盖生产库（会要求输入大写 YES，并自动先做一次即时备份）
/opt/fcmediaagent/ops/restore-prod.sh /opt/fcmediaagent/backups/mysql/fcmediaagent-20261112-033000.sql.gz --apply

# 4) 起服务并验证
systemctl start fcmediaagent-api fcmediaagent-worker
curl -fsS http://127.0.0.1:3000/health   # 期望 {"status":"ok","db":"up"}；db 为 down 说明连不上 MySQL，看 /opt/fcmediaagent/logs/api.log
```

`--apply` 的保护：模式横幅 + 必须手动输入 `YES`（不是 y）+ 导入前自动调用 `backup-prod.sh` 做即时备份（即时备份失败会直接中止，不会覆盖生产库）。

### 5.3 紧急逃生

如果 `--apply` 后发现问题：用刚才的即时备份再 `--apply` 回去。即时备份文件名会打印在输出里，形如 `/opt/fcmediaagent/backups/mysql/fcmediaagent-<恢复前时间戳>.sql.gz`。

## 6. OSS 配置

`oss-upload.mjs` 从 `/opt/fcmediaagent/app/.env` 读以下变量（与仓库 `scripts/_env.mjs` 一致）：

```
OSS_REGION=oss-cn-...            # 必填
OSS_ACCESS_KEY_ID=...            # 必填
OSS_ACCESS_KEY_SECRET=...        # 必填
OSS_BUCKET=zhongke001            # 必填
OSS_ENDPOINT=...                 # 可选，自定义 endpoint 时才写
```

- 用 `createRequire` 从 `/opt/fcmediaagent/app` 解析 `ali-oss`（即生产机 `app/node_modules` 里的那份），不额外装依赖；
- 连接固定 `secure: true`（HTTPS）；
- 大于 8MB 走 `multipartUpload`（`partSize: 8MB`，并行 3），小于 8MB 走 `put`；
- 上传后 `head(key)` 校验远端 `content-length` 与本地大小一致才算成功；
- 解析不到 `ali-oss`、或 `.env` 缺 `OSS_*`，退出码 **2** 并打印中文提示（不会抛栈）。

手动确认桶可用：

```bash
/opt/node/bin/node /opt/fcmediaagent/ops/oss-upload.mjs --dry-run /opt/fcmediaagent/backups/mysql/<任意备份>.sql.gz
```

## 7. 故障处理

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `错误：找不到环境文件 /opt/fcmediaagent/app/.env` | 部署路径不对或跑在错误主机 | 确认在生产机、且 `app/.env` 存在 |
| `错误：在 .env 里没找到 DATABASE_URL` | `.env` 缺键或被注释 | 补 `DATABASE_URL=mysql://user:pass@127.0.0.1:3306/fcmediaagent` |
| `错误：找不到 docker 命令` | 非生产机 / PATH 不含 docker | 生产机上执行；systemd 单元已用绝对路径脚本，不受 PATH 影响 |
| `错误：容器 fcm-mysql 不存在或 docker 不可用` | 容器名变了或 docker 挂了 | `docker ps -a --filter name=fcm-mysql` |
| `错误：容器 fcm-mysql 未在运行` | 容器停了 | `docker start fcm-mysql` |
| `mysqldump 被 MySQL 拒绝（Access denied）` | 账号权限不足 | 看到 `.env` 里的 DATA 账号需要 SELECT/LOCK TABLES/SHOW VIEW/TRIGGER/EVENT 权限；`--no-tablespaces` 已规避 PROCESS 那类报错 |
| `gzip 完整性校验失败` | 磁盘满或 pipe 中断 | 看 `df -h /opt`，清磁盘后重跑 |
| `警告：分区可用空间不足 1GB` | 磁盘紧张 | 先清 `backups/mysql` 旧文件或改 `RETENTION_DAYS` |
| `警告：OSS 上传失败` | 网络/凭据/桶权限 | 本地备份仍有效；用 `--dry-run` 单测 `oss-upload.mjs`，缺 `.env` 变量时退出码为 2 |
| `restore: --to-db 只允许字母、数字、下划线` | 库名非法 | 用 `fcm_restore_xxx` 这类名字 |
| systemd 单元 `failed` 但备份文件在 | 极少见：清理阶段或 OSS 阶段报错 | `journalctl -u fcmediaagent-backup.service -n 50`，脚本每步都有中文原因 |

## 9. 未验证点与已知限制

1. **没有在生产机上跑过真实 mysqldump**：本机（Windows）没有 docker/MySQL，脚本只用「docker 存根」验证了完整控制流（导出→gzip→`gzip -t`→sha256→清理→OSS warn 分支→失败分支退出码 1 与 `.partial` 清理）。真实库上的权限、字符集、数据量表现待首次上线验证。
2. **`--apply` 未演练**：覆盖生产库的路径（含即时备份 + YES 确认 + 导入）只做过 `--dry-run` 打印，没有在真库上执行。
3. **OSS 真实上传未验证**：本机没有 `ali-oss`，只验证了「解析不到依赖时打印中文提示并退出码 2」；生产机首次上传需人肉确认一次（`--dry-run` 会打印 `oss://<bucket>/backups/mysql/<file>`）。
4. **临时库不受 `--apply` 保护限制**：演练会真的在 MySQL 里建库，需要账号有 `CREATE`/`DROP` 权限；若账号只有数据权限，演练会失败——此时请联系 DBA 用 root 账号跑演练，或先临时授权。
5. **备份文件本身未加密**：`.sql.gz` 落盘为明文 SQL 压缩包，权限依赖 `/opt/fcmediaagent/backups` 目录属主（建议 `chmod 700` 且属主 root）；异地备份请确认 OSS 桶是私有读。
6. **未做备份到另一台机器**：只在同机 + OSS 两层，磁盘整机损坏时依赖 OSS 恢复；`oss-upload.mjs` 不做下载/回拉，异地恢复需先 `ossutil` 或控制台下载再 `restore-prod.sh`。
