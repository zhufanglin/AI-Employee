# T-40 媒体任务取消 / 重生成 + 真机升级演练

> 2026-11-07 ｜ 背景：主线小项（生成页无取消/重生成、真机升级未演练）落地记录。

## 1. 取消（服务端）

原版与复刻此前都只有「提交 → 轮询 → 结算/退款」，用户一旦点错参数就只能等 3–4 分钟或等失败退款。现在补了取消。

### 接口

- `POST /api/media/tasks/:taskId/cancel`（JWT，仅本人任务）
  - 未终态（`QUEUED`/`RUNNING`/`SUBMITTING`/`REVIEW`）→ 调 RunningHub 取消 + 本地置 `CANCELLED` + **全额退回预扣积分**（`settledAmount=0`），返回体带 `resultMeta.cancel`（`{ ok, code, msg }`）说明上游结果。
  - 已终态（`SUCCESS`/`FAILED`/`CANCELLED`）→ `409 任务已结束，无法取消`。
  - 别人的任务 → `404 媒体任务不存在`。

### 上游取消接口

`POST {RUNNINGHUB_BASE_URL}/task/openapi/cancel`，body `{ apiKey, taskId }`（**apiKey 放 body，不是 Authorization**）。实测：
- 不存在的 taskId → `{"code":807,"msg":"APIKEY_TASK_NOT_FOUND"}`
- 真实排队任务 → `{"code":0,"msg":"success"}`

上游不可用/已结束时**不阻断本地退款**，只把原因记在 `resultMeta.cancel`。

### 关键防回弹

`getTask()` 对 `CANCELLED` 直接返回本地记录、不回查上游；`webhook()` 对 `CANCELLED` 直接忽略。原因：取消瞬间上游可能还回 `QUEUED`/`RUNNING`，回写会把状态顶回"生成中"而钱已退，用户会看到"还在跑但没结果"。

代码位置：
- `packages/server/src/media/media.service.ts`：`cancelTask()`、`cancelUpstream()`、`refundFailure(..., finalStatus)`（现在支持 `FAILED`/`CANCELLED`，且不再对 `CANCELLED` 二次退款）、`getTask()`/`webhook()` 的取消守卫。
- `packages/server/src/media/media.controller.ts`：`@Post("tasks/:taskId/cancel")`。

## 2. 桌面端

- `packages/desktop/src/main/index.ts`：`ipcMain.handle('media:cancel', ...)` 转发到上面接口。
- `packages/desktop/src/preload/index.ts`：`fcm.media.cancel(id)`。
- `packages/desktop/src/renderer/src/pages/MediaCreation.tsx`：
  - 排队中/生成中 → 显示「取消任务（全额退回积分）」；
  - 失败/取消/成功 → 显示「按当前参数重新生成」（复用当前表单参数重新走一次提交流程，重新预扣、重新计价）；
  - 取消后立即刷新积分余额，状态文案「已取消（积分已退回）」。

「重生成」目前是**按当前表单参数重新提交**（原版/复刻都没存提交快照），所以从历史里翻旧任务不能一键重生成——这是本次的有意取舍，避免给 `MediaTaskRecord` 加 `requestJson` 大字段。

## 4. 真机升级演练（0.1.0 → 0.1.1）

演练思路：本机装 0.1.0 → 用 `FCM_UPDATE_URL` 指到本地更新源 → 通过 CDP 调用渲染层真实暴露的 `window.fcm.update.{check,status,download,install}`（就是设置页那三个按钮走的同一套 IPC）→ 验收安装后的 exe 版本。

产物与脚本：
- `_deploy/upgrade/v0.1.0.exe`：上一版安装包（127,731,716B）留档。
- `_deploy/upgrade/serve.mjs`：本地静态源，支持 Range（206），默认 `_deploy/upgrade/www`、:8899。
- `scripts/rehearse-upgrade.mjs`：静默装 0.1.0 → 起 0.1.0 带 `--remote-debugging-port=9222` → Node 内置 WebSocket 连 CDP → check/download/install → 轮询安装目录 exe 的 ProductVersion 断言 0.1.1。支持 `FCM_REHEARSE_SKIP_INSTALL`/`FCM_REHEARSE_EXPECT_INSTALLED`/`FCM_REHEARSE_EXPECT_SILENT`。
- 用户侧入口：设置页「检查更新 / 下载新版本 / 重启并安装」（`packages/desktop/src/renderer/src/pages/Settings.tsx:33-35`）。

### 第一次演练发现的问题（已修）

0.1.0 → 0.1.1 时长出一个**交互式安装向导**（进程名 `fcmediaagent-ai-employee-0.1.1-win-x64`，窗口标题「中科元晟 AI员工 安装」，一直等人点下一步）。日志证明调用参数是：

```
[updater] Install: isSilent: false, isForceRunAfter: true
[updater] Executing: ...0.1.1-win-x64.exe with args: --updated,--force-run
```

根因：`packages/desktop/src/main/update.ts:89` 写的是 `autoUpdater.quitAndInstall(false, true)`。第一个参数是 **isSilent**，false 时 electron-updater 不会加 `/S`，NSIS 就走向导模式。更糟的是 `autoInstallOnAppQuit = true`，用户正常关软件也会莫名弹出安装界面。

修复：改为 `autoUpdater.quitAndInstall(true, true)`（并加注释说明两个参数的含义）。重建后 `out/main/index.js:607` 为 `electronUpdater.autoUpdater.quitAndInstall(true, true);`。

### 演练结果

1) **0.1.0 → 0.1.1（升级本身可用）**：CDP `check` 返回 `available 0.1.1` → `download` 下载 127,731,706B → `install` 触发安装；因旧版本传的是 isSilent=false，出现向导，脚本用 `WScript.Shell.AppActivate + SendKeys("{ENTER}")` 模拟点击后完成，安装目录 `%LOCALAPPDATA%\Programs\fcmediaagent-desktop\中科元晟 AI员工.exe` 的 ProductVersion 由 `0.1.0.0` 变为 **`0.1.1.0`**。⇒ 更新链路（feed → 下载 → 安装 → 版本替换）已验证。
2) **0.1.1 起为静默安装（新代码已验证）**：用一份伪造的 `0.1.2` feed（内容就是 0.1.1 的字节改名）驱动同一个 CDP 流程，日志为

```
[updater] Install: isSilent: true, isForceRunAfter: true
[updater] Executing: ...0.1.2-win-x64.exe with args: --updated,/S,--force-run
UPGRADE REHEARSAL OK (0.1.0 -> 0.1.1.0)
```

全程**没有出现任何安装窗口**，安装结束后应用被自动拉起（进程 `中科元晟 AI员工`，窗口标题「中科元晟 AI 员工」）。⇒ 0.1.1 之后所有升级对用户都是无感的。

3) 差分下载回退属正常：feed 里没有旧版本 blockmap，日志会出现 `Cannot download differentially, fallback to full download: ... 0.1.0-win-x64.exe.blockmap 404`，electron-updater 自动改全量下载，不影响结果（我们只发全量包）。

### 已知取舍

- **0.1.0 → 0.1.1 这一次仍会弹向导**：调用参数由客户端旧代码决定，改不了。用户点一次「安装」即可，之后版本全程静默。
- 更新包未做代码签名（`signExecutable: false`），SmartScreen 可能提示「未知发布者」；正式对外发售前应上签名证书。
