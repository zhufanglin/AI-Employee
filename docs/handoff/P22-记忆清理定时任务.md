# P22 记忆清理定时任务

> 完成时间：2026-11-08　｜　看板：T-50　｜　能力层：`memory_dedupe`（P21）+ 定时外壳（P22）

## 1. 为什么做

P21 把「存量重复记忆清理」做成了 `memory_dedupe` 能力，但要人手动跑 CLI 才会执行。老板不会每周记得跑，而记忆只增不减时，重复条目会让 `memory_search` 的候选变脏（同一条事实的两种写法都进重排列表），也会让 `hitCount` 分散。

所以补一个**进程内定时任务**：每周日凌晨 3 点对所有「记忆条数 ≥ 20」的用户自动跑一次 `mode=apply`，把重复项合并掉。

## 2. 设计取舍

| 选择 | 方案 | 理由 |
| --- | --- | --- |
| 调度器 | 原生 `setTimeout` 自排程 | 只有「每周固定时刻」一个周期，不需要 cron 表达式解析；不引入 `@nestjs/schedule` / `node-cron`，避免生产 `npm install --no-save` 被 prune 的坑（P16 事故） |
| 时区 | 固定 `Asia/Shanghai`，用 UTC 偏移手算 | 生产机是 UTC 时区，业务全在中国；不依赖系统 TZ 环境变量 |
| 执行入口 | 直接调 `CapabilityService.run` | 定时与手动（CLI/接口）走**同一条代码路径**，行为、限额、返回结构完全一致，不会出现两套逻辑 |
| 清理范围 | 只跑记忆条数 ≥ `MEMORY_CLEANUP_MIN_ROWS`（默认 20）的用户 | 记忆少时无可清；避免给几百个空用户反复打模型（省钱、省时） |
| 失败处理 | 单用户失败/异常只计数，不中断整轮 | 一个用户记忆脏数据不该阻断其他用户 |
| 开关 | `MEMORY_CLEANUP_ENABLED=0` 直接不排程 | 出问题时无需改代码/回滚，改 env + restart 即可停 |

## 3. 排程算法

`nextWeeklyRun(now, hour = 3)`：

1. `wall = now + 8h`（把 UTC 平移到「上海墙上时间」，之后全部用 `getUTC*` 读）；
2. `weekday = wall.getUTCDay()`（0 = 周日）；
3. `todayAtHour = Date.UTC(y, m, d, hour, 0, 0, 0)`；
4. `daysAhead = (7 - weekday) % 7`；若 `daysAhead === 0 && wall >= todayAtHour`（今天就是周日但已过点）则 `daysAhead = 7`；
5. 返回 `new Date(todayAtHour + daysAhead * 86400000 - 8h)`。

实测（单测断言）：

| 现在（上海） | 下次执行（UTC） | 下次执行（上海） |
| --- | --- | --- |
| 11-08 周日 02:00 | `2026-11-07T19:00:00.000Z` | 11-08 03:00 |
| 11-08 周日 04:00 | `2026-11-14T19:00:00.000Z` | 11-15 03:00 |
| 11-11 周三 12:00 | `2026-11-14T19:00:00.000Z` | 11-15 03:00 |
| 11-07 周六 18:00 | `2026-11-07T19:00:00.000Z` | 11-08 03:00 |
| 11-11 周三 12:00，hour=5 | `2026-11-14T21:00:00.000Z` | 11-15 05:00 |

## 4. 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `MEMORY_CLEANUP_ENABLED` | `1` | `0/false/off/no` 关闭排程（手动调用仍可用） |
| `MEMORY_CLEANUP_HOUR` | `3` | 0–23，非法值回落 3 |
| `MEMORY_CLEANUP_MODE` | `apply` | 非 `report` 的值一律按 `apply` |
| `MEMORY_CLEANUP_LIMIT` | `60` | 每用户最多扫描 60 条（1–60） |
| `MEMORY_CLEANUP_MIN_ROWS` | `20` | 记忆条数低于此值的用户跳过 |

## 8. 踩过的坑

1. **单测里 `withEnv` 必须是 async**：最初写成同步函数 + `finally` 恢复 env，异步回调里 `await` 之后才读 env，读到的已经是恢复后的值 → 误判「阈值可调」失败。改成 `async function withEnv(pairs, fn) { try { return await fn(); } finally { … } }`。
2. **Prisma 6 的 `groupBy` 类型不接受 `_count: { _all: true }`** 的写法（TS2345），聚合结果还要 `as any` 放宽；上线前 tsc 必须 0。
3. **验证脚本里读内存状态不能只看返回值**：`status().nextAt` 在 `onApplicationShutdown` 后仍然保留（只是定时器清了），所以「关闭」的断言要看 `enabled` 而不是 `nextAt === null`。
4. **`.ps1` 编辑后必丢 BOM**：每次 `tools.edit` 之后都要 `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))` 重写，并复查字节头 `239,187,191`，否则 `powershell -File` 按 GBK 解码报 ParserError。
5. **`tools.edit` 的 `file changed since it was read`**：BOM 重写会刷新文件状态，下一次 edit 前必须重新 `read`。
6. **Nest 的 POST 默认返回 201**：管理端「手动跑一轮」语义是执行动作不是创建资源，必须显式 `@HttpCode(HttpStatus.OK)`；生产验收首轮就是因为断言 200 而拿到 201 假失败。
7. **后台 job 卡在 `running` 但验证其实早就跑完**：`verify.ps1` 里 `Start-Process` 起的本地服务继承了标准句柄，脚本 `exit` 后子进程仍持有管道，dsh 认为 job 未结束。判断方式看 `docs/handoff/last-verify.json` 的 `at`/`ok`，别只信 job 状态。

## 9. 还没做

- 桌面端没有入口：状态和手动触发目前只能走管理端 HTTP（或 `run-memory-dedupe.mjs`），老板在客户端看不到「上次清理了什么」。
- 没有「多实例只跑一个」的分布式锁：目前生产单实例没问题，横向扩容后每个实例都会排程。
- 没有补跑：服务在周日 03:00 停机时，这一周就跳过（`lastRunAt` 也没落库，重启后不补）。
- 桌面端「记忆管理」页仍未做（可以看到/删除/手动合并记忆）。
