# P39 员工技能改造规范（SKILL.md 接真实工具）

> 背景：17 个员工技能的 SKILL.md 只描述了业务动作，**没有一个提到真实存在的工具名**，
> 其中 3 个还要求 `python scripts/video_cli.py`、`xhs-cli`、`wechat_cli.py` 这类员工运行环境里
> 根本不存在的 CLI，导致「员工看着专业、实际干不了活」。本规范用于统一改造。

## 一、硬约束（违反任何一条即返工）

1. **只能引用下面列出的能力名**，不得出现 python / node / ffmpeg 命令行、不得引用 `scripts/xxx.py`、
   `references/xxx.md`、`xhs-cli`、`apollo`、Whisper、auto-editor、CRM 系统、任何"需要安装"的东西。
2. **frontmatter 的 name 与 description 保持原样**（description 可微调去掉 CLI 字样，但不得改语义、不得加长超过原长 1.5 倍）。
3. **保留原有业务语义**：拆解维度、输出表格列、判断标准、话术风格都照原样留，只把"用什么做"从假 CLI 换成真工具。
4. **字节数 ≤ 7500**（系统按 8000 字符截断，超了会切掉结尾）。
5. 全中文，Markdown，不要 emoji 图标堆砌，不要写"作为 AI 助手"之类废话。
6. 不允许声称已经发布/已经生成文件/已经剪辑——除非确实调用了对应工具。

## 二、真实可用能力清单（service = 服务端能力，media = 媒体生成，local = 只在本机执行）

| 能力名 | 用途 | 关键参数 |
|---|---|---|
| `web_search` | 联网搜索，返回标题/链接/摘要 | `{query}` |
| `web_extract` | 抓单个网页正文纯文本 | `{url}` |
| `web_batch` | 一次抓最多 5 个 URL | `{urls:[...]}` |
| `llm_text` | 站内模型生成/改写/总结 | `{instruction, input}` |
| `file_write` | 写文本文件到工作区，返回下载链接 | `{name, content}` |
| `file_list` | 列工作区文件（含用户上传资料） | `{}` |
| `file_read` | 读文本文件（md/txt/csv/json/html/xml/log） | `{name 或 key, maxChars}` |
| `file_delete` | 删工作区文件 | `{name 或 key}` |
| `doc_read` | 读 xlsx/docx/pdf 内容 | `{name 或 key, maxChars}` |
| `doc_write` | 生成真 Excel(.xlsx) / Word(.docx) | xlsx: `{format:"xlsx", name, sheets:[{name,rows}]}`；docx: `{format:"docx", name, content:<markdown>}` |
| `media_info` | ffprobe 读时长/分辨率/编码 | `{source}` |
| `media_process` | 剪辑/转码/抽音轨/压缩/截图/拼接 | `{op:"trim|extract_audio|transcode|compress|thumbnail|concat", source, ...}` |
| `image_understand` | 看图（识别/抄字/判断风格） | `{source, question}` |
| `image_gen` | 文生图（**付费、约 3–5 分钟**） | `{prompt, size?}` |
| `video_gen` | 图生视频（**付费、约 3–5 分钟**） | `{image, prompt?}` |
| `content_save` | 存一条素材到内容库 | `{title, url?, summary?, category?}` |
| `content_query` | 查内容库 | `{category?, mustUse?, used?}` |
| `distribution_save` | 记录今日分发 | `{summary, ...}` |
| `customer_save` | 录一条潜在客户 | `{company, wechatNickname?, industry?, position?, interaction?, lastCommDate?, addWechatDate?}` |
| `customer_query` | 按条件筛客户 | `{company?, wechatNickname?, industry?, lastCommDays?, addWechatDays?}` |
| `memory_save` | 存长期记忆（自动查重合并） | `{content, kind?}` |
| `memory_search` | 语义检索记忆（执行器自动带上下文） | `{query}` |
| `memory_list` / `memory_delete` | 列/删记忆 | `{}` / `{id}` |
| `employee_dispatch` | 把活派给另一个已安装员工 | `{employeeSlug, input}` |
| `employee_task_status` | 查派出去的任务 | `{taskId}` |
| `cron_create` / `cron_list` / `cron_delete` | 定时任务（5 段 cron） | `{employeeSlug, cron, input, title?}` / `{}` / `{cronId}` |
| `platform_publish` | 抖音/小红书/视频号发布（**只在本机客户端执行**） | `{platform:"douyin|x iaohongshu|shipinhao", type:"video|image", mediaPaths:[...], title, content}` |
| `platform_status` | 三平台登录态（本机） | `{platform?}` |
| `platform_stats` | 创作后台数据快照（本机） | `{platform}` |

> 注意：平台发布/取数只在用户自己电脑的客户端里执行；云执行器调用会返回中文提示「需要在桌面端执行」。
> 员工交付文案必须据此区分「已在本机发布」和「给出发布方案，需在客户端执行」。

## 三、每个 SKILL.md 必须新增的两节

### 1) `## 工具编排`（关键，写 4–8 步，顺序即执行顺序）

写法示例（BOSS 线索雷达）：

```markdown
## 工具编排

1. `file_list` 看工作区有没有「企业基础资料.md」「客户资料.xlsx」；有就 `doc_read` / `file_read` 读，把它们当行业、产品、区域的默认值。
2. `web_search` 用 2–4 个不同角度的关键词搜目标客户（"广州 跨境电商 公司 招聘 采购"），再用 `web_extract` 打开每个候选官网核实业务范围。
3. `web_batch` 一次最多抓 5 个官网，凑够 10–15 个候选。
4. 逐条打分：行业匹配、规模、可触达信号（招聘/新店/融资）、决策人可识别度，各 1–5 分。
5. `doc_write`（format=xlsx）导出线索表，列：公司、官网、城市、行业、规模线索、需求信号、匹配分、触达理由、来源链接。
6. `customer_save` 把匹配分 ≥4 的线索写进客户库，方便后续跟进。
7. 正文里先给"最值得先联系的 5 家 + 理由"，再给文件下载名。抓不到官网的线索要标注「未核实」。
```

### 2) `## 交付前自检`（必须包含下面四条，可换措辞）

- 表格里的公司名、数字、链接是否都来自 `web_search`/`web_extract` 的真实结果？没有来源的一律标「未核实」。
- 是否真的生成了交付文件？生成了就在正文写出文件名；没生成就不许说"已导出"。
- 用户给的信息不足时，先用 `file_list` 找资料，再 `memory_search` 查历史，最后才向用户提 1–2 个最关键的问题。
- 输出长度控制在 800–2500 字，先给结论和执行清单，再给证据与明细。

## 四、分工与验收

- 每个员工改完自己跑 `node scripts/gen-skills-content.mjs` 前**不要**执行生成脚本（由 Lead 统一生成，避免并发写同一个文件）。
- 自检：`node -e` 读文件算字节数 + 用正则确认没有 `python `、`\.py`、`xhs-cli`、`ffmpeg ` 字样 + 确认含 `## 工具编排` 与 `## 交付前自检`。
- 交付时回报：员工 slug、字节数、删掉了哪些假 CLI、编排了几步、映射了哪些真实能力。
