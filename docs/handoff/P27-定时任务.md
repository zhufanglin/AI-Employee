## 主进程导出签名

```ts
export interface CronOpsDeps {
  api: (path: string, init?: any) => Promise<any>
}

export interface CronItem {
  cronId: string
  employeeSlug: string
  employeeName: string
  cronExpr: string
  timezone: string
  enabled: boolean
  nextRunAt: string | null
  lastRunAt: string | null
}

export interface CronCreateInput {
  employeeSlug: string
  cronExpr: string
  timezone?: string
  workflowKey?: string
  title?: string
}

export type CronOpResult<T = any> = { ok: true; data: T } | { ok: false; error: string }

export function registerCronOps(ipc: IpcMain, deps: CronOpsDeps): void
```

`deps.api` 直接复用 `main/index.ts` 里已有的封装（已带 JWT、已解析 JSON）。主进程只向它发：

```ts
api('/capabilities/run', {
  method: 'POST',
  body: JSON.stringify({ name, params })
})
```

### IPC 通道与返回

| 通道 | 入参 | 成功返回 `data` | 失败 `error` |
| --- | --- | --- | --- |
| `cron:list` | 无 | `{ items: CronItem[], total: number }` | 服务端中文原文 |
| `cron:create` | `CronCreateInput` | `{ cronId: string, nextRunAt: string \| null }` | 服务端中文原文 |
| `cron:delete` | `{ cronId: string }` | `{ deleted: true }` | 服务端中文原文 |

三个通道统一返回 `{ ok: true, data }` 或 `{ ok: false, error }`，handler 不会向外抛异常。

### 关键实现说明

- **HTTP 201 也是失败**：服务端业务失败仍返回 201，真正的成败在 `body.success`，中文文案在 `body.error`。`cron-ops.ts` 显式判断 `body.success === false` 并原样透传 `body.error`，不根据状态码判断（`main/index.ts` 的 `api` 对 201 也不会 throw）。
- **字段兼容**：服务端 `cron_list` 实际返回 `employee: { slug, name }`，契约写的是扁平 `employeeSlug`；`normalizeItem` 两种都兼容，并统一成 `employeeSlug` / `employeeName`。
- **本地校验**：`create` 先校验 `employeeSlug`（`员工 slug 必填`）、`cronExpr`（`cron 表达式必填`）和 5 段格式（`cron 表达式必须是 5 段（分 时 日 月 周），例如 0 9 * * *`）；`delete` 校验 `cronId`（`cronId 必填`）。校验失败不发请求。
- **时区缺省**：未传 `timezone` 时主进程补 `Asia/Shanghai`，与服务端默认值一致。
- **网络异常**：`api` 抛错时返回 `连接定时任务服务失败：<原因>`，不把异常抛给渲染进程。
- **创建缺少 id**：`cron_create` 返回成功但无 `cronId` 时返回「服务端没有返回定时任务 id，请刷新列表确认是否已创建」，避免页面误报成功。

## 冒烟测试

运行（仓库根目录）：

```powershell
node scripts/smoke-p27-cron.mjs
```

做法：`esbuild.buildSync` 把 `cron-ops.ts` 打成 CJS（`external: ['electron']`），用 `new Function` 加载；注入只实现 `handle` 的假 `ipcMain`（收集回调）和记录请求的假 `api`，直接调用 handler。

覆盖项：

1. 注册三个通道；
2. `cron_list` 成功、请求路径/方法、能力名与空参数、两种员工字段归一化、`total`、时间与 `enabled`；
3. `cron_create` 成功、参数、缺省时区、返回 `cronId/nextRunAt`；
4. 服务端 `success:false`（HTTP 201）透传中文错误且不带 `data`；
5. `cron_delete` 的 201 + `success:false`（「定时器不存在」）；
6. 缺员工 slug、缺 cron、cron 非 5 段、缺 `cronId` 的本地校验，且不发请求；
7. `cron_delete` 成功且 `cronId` 原样传给服务端；
8. `api` 抛错时返回 `ok:false` 不崩溃。

结果：

### 2. preload/index.ts

在 `api` 对象里新增（方法名与页面调用一致）：

```ts
cron: {
  list: () => ipcRenderer.invoke('cron:list'),
  create: (input: {
    employeeSlug: string
    cronExpr: string
    timezone?: string
    workflowKey?: string
    title?: string

```

- `create` 入参 `{ employeeSlug, cronExpr, timezone?, workflowKey?, title? }`；
- `remove` 入参 `{ cronId }`，底层通道是 `cron:delete`（页面方法名叫 `remove`）。
