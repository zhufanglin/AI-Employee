# P14 上游网络抖动加固与渠道失败文案

## 1. 问题（2026-11-07 16:36 生产实例）

用户从微信发来一段真实需求（本地少儿英语培训招生方案），几秒内就收到「任务处理失败：Bad Gateway Exception」。

生产证据链：

- `api.log`：`渠道任务已创建 task=cmw65frf6004przlb7ts9494z channel=personal-wechat from=朱方林 employee=boss-lead-radar` → 2 秒后 `[ProvidersService] upstream fetch failed (attempt 1/2): fetch failed` → `渠道结果已推送`。
- `worker.log`：`claimed ... [personal-wechat] 你好，我是做本地少儿英语培训的…` → 1 秒后 `failed ... Bad Gateway Exception`。
- 同一账号 3 分钟前的同类任务 `cmw65bx5r003vrzlbkv3zfbyj` 正常耗时约 2 分钟完成 ⇒ 不是额度、不是权限、不是模型不可用，是**单次网络抖动**。

根因两条：

1. `packages/server/src/providers/providers.service.ts` 的 `fetchWithRetry` 只重试 1 次、退避固定 400ms，容错窗口约 1 秒；跨境出口（火山方舟 `ark.cn-beijing.volces.com`）抖动一次就整单失败。
2. 失败文案把内部异常原文（`Bad Gateway Exception`）直接推给微信用户，用户不知道该干什么。

顺带排查到 DNS 隐患：生产机 `getent hosts ark.cn-beijing.volces.com` 返回 **IPv6** 地址，而该机没有 IPv6 默认路由（`curl -6` 直接失败，`curl -4` 返回 401 说明 IPv4 通），Node 默认 `--dns-result-order=verbatim` 有一定概率先连 IPv6 而失败。

## 2. 改动

### 2.1 重试策略（providers.service.ts）

```ts
/** 上游网关类 5xx：重试通常能过；4xx 是参数/额度问题，重试没意义。 */
const GATEWAY_STATUS = new Set([500, 502, 503, 504, 529]);

private async fetchWithRetry(url: string, init: RequestInit, attempts = 3): Promise<Response> {
  // 网络异常重试 3 次（退避 400 * 3 ** i = 0.4s / 1.2s / 2.4s），网关类 5xx 也重试
}
```

最终仍失败时抛 `BadGatewayException`，message 为「上游网络不可达，请稍后重试（…）」，code 为 `UPSTREAM_UNREACHABLE`。

### 2.2 渠道失败文案（channels/dispatcher.service.ts）

```ts
/** 这些失败属于上游网络/网关抖动，重发通常就好，文案改成引导重试。 */
const TRANSIENT_FAILURE = /Bad Gateway|Gateway Timeout|Service Unavailable|UPSTREAM_UNREACHABLE|上游网络不可达|fetch failed|ECONNRESET|ETIMEDOUT|socket hang up|timeout|超时|502|503|504/i;
```

- 命中：日志 `渠道任务失败（可重试） task=… reason=…`，微信收到「这次没跑成功（服务端临时波动，通常是模型接口网络抖动）。把需求原样再发一遍就行，我会重新执行。」
- 未命中（如余额不足、参数错误）：仍然「任务处理失败：<原因>」，因为重发也没用，必须让用户看到真实原因。

### 2.3 DNS 优选 IPv4（systemd）

`fcmediaagent-api` 与 `fcmediaagent-worker` 都加了 `--dns-result-order=ipv4first`：

```
Environment=NODE_OPTIONS=--max-old-space-size=768 --dns-result-order=ipv4first   # api
Environment=NODE_OPTIONS=--dns-result-order=ipv4first                           # worker
```
改完 `systemctl daemon-reload` + 重启；原 unit 备份为 `*.service.bak.<ts>`。

## 4. 经验

- **重试窗口要覆盖真实抖动**：1 秒窗口对跨境 API 太窄；3 次指数退避（合计 4 秒）+ 网关 5xx 重试是性价比最高的做法，不必上队列重放。
- **对渠道用户不要抛原始异常**：他们看不到后台日志，也不懂 Gateway；能自救的（重发）就给动作，不能自救的（额度、参数）才给原因。
- **DNS 返回 IPv6 但机器没 IPv6 路由**是隐蔽故障源：`getent hosts` + `curl -6` / `curl -4` 对比能在 1 分钟内确认；`--dns-result-order=ipv4first` 是低成本保险。
- worker 日志里 `init retry fetch failed` / `poll error fetch failed` 是本机到 127.0.0.1 的瞬时失败，服务会自动恢复，不必当成事故。

## 5. 复跑结果（2026-11-07 08:49–08:53 UTC）

- 任务 `cmw65x81y000qrz77o2sr41zo`（title「真实需求验收-少儿英语招生」，boss-lead-radar，executor=cloud），输入就是用户原话原文。
- worker：`08:49:52 claimed` → `picked model boss-lead-radar` → `model = doubao-seed-2-0-lite skillChars = 1173` → **`08:53:26 done`**（3 分 34 秒，无 failed、无 Bad Gateway）。
- DB：`status=awaiting_approval`、`outputText` **11,724 字符**、`error` 为空。
- 产出开头：「本次按公开研究模式完成，基于番禺区教育局公开提示、本地/连锁机构公开招生信息整理」→ 合规红线（双减、暑假学科类禁培、收费不超 3 个月/60 课时/5000 元、合同示范文本，带番禺区教育局链接）→ 家长关心的 5 件事 → 同行打法 → 朋友圈文案与家长画像。
- 结论：同样的输入加固前 1 秒内 failed，加固后完整跑完 ⇒ 抖动被重试吃掉。

## 6. 仍可改善（未做）

- 渠道回推只有前 1500 字：客户常要长文档时，可以把完整结果 `file_write` 落 OSS 并把链接一起发。
- 重试是同步的（最坏约 4 秒），没有任务级重放；上游分钟级故障仍需重发或后台重跑。
