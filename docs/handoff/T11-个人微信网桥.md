## 3. 契约实现对照

| # | 方法与路径 | 实现位置 | 说明 |
|---|---|---|---|
| 1 | `GET /api/v1/bot/status` | `app.py:bot_status` + `wechat_ui.py:status` | 读不到微信时降级 `logged_in:false`，HTTP 仍 200 |
| 2 | `GET /api/v1/memory/list` | `app.py:memory_list` | limit 1~500 / offset≥0；真实模式来自当前会话列表 |
| 3 | `GET /api/v1/chat/messages` | `app.py:chat_messages` | `chat_name` 必填；升序；最多 200 |
| 4 | `POST /api/v1/chat/send` | `app.py:chat_send` | 空 name/msg 分别 400；humanize 分段 |
| 5 | `POST /api/v1/chat/send-file` | `app.py:chat_send_file` | file_path / file_url 二选一；URL 下载后发送 |
| 6 | `POST /api/v1/chat/listen-list` | `app.py:chat_listen_list` | wxid/nickname 至少一个；返回累计 following |
| - | `GET /healthz` | `app.py:healthz` | 无鉴权，纯文本 `ok` |

错误统一 `{ "ok": false, "code": "...", "message": "..." }`；401 为 `UNAUTHORIZED`，参数错误 400，UI 连续失败 503 `WECHAT_UI_BUSY`。

## 4. 关键设计 / 决策

1. **选 wxauto 而非 uiautomation**：wxauto 封装了 `ChatWith/SendMsg/SendFiles/AddListenChat/GetAllMessage`，正好覆盖 6 契约；uiautomation 需自研控件树、剪贴板、文件发送。wxauto PyPI 已下架，因此 `requirements.txt` 锁定 GitHub commit `05e5a52379c99f401dc512acfdd811b3d701da8b`（archive.zip，目标机无需 git）。
2. **单实例锁**：同一台机器只能有一个进程操作微信 UI；Windows 用 `msvcrt.locking` 对锁文件首字节加独占锁，进程崩溃由 OS 释放。第二进程启动会在 lifespan 阶段报错退出。
3. **UI 串行化**：所有真实 UI 操作走 `_execute`：`threading.Lock` 等待最多 `WECHAT_BRIDGE_UI_TIMEOUT`（默认 30s），失败重试 `WECHAT_BRIDGE_UI_RETRY`（默认 2，即最多 3 次），仍失败 503 `WECHAT_UI_BUSY`。状态接口例外：失败降级 `logged_in:false`，避免上游误判整体不可用。
4. **监听与 HTTP 分离**：`ListenerService` 独立 daemon 线程；拿 UI 锁只等 0.5 秒，拿不到就跳过本轮，不做重试，防止轮询饿死发送请求。
5. **发送重试不重发已发段**：`send` 在闭包里记录 `segments_sent`，重试从上次中断处继续；降低重复发送风险。
6. **Mock 与真实后端同形**：两者都实现 `status/contacts/messages/send/send_file/listen_list/poll/close`，HTTP 层零分支；Mock 预置 Stu/Amy/文件传输助手，任意会话首读 5 条，相同 `(name,msg)` 5 秒幂等。
7. **鉴权**：`WECHAT_BRIDGE_TOKEN` 非空时严格校验 `Bearer`，`hmac.compare_digest` 恒定时间比较；为空启动 warning 但放行，仅本机调试。
8. **错误处理**：`ApiError` 统一处理；`RequestValidationError` 转 400 `VALIDATION_ERROR`；404/405 也包成统一 JSON；未捕获异常 500 `INTERNAL_ERROR` 并写日志。
9. **日志**：控制台 + `WECHAT_BRIDGE_LOG_DIR/bridge.log`，5MB × 5 轮转；启动日志不打印 Token 明文。

## 6. 上线门槛（一句话）

必须在装有**微信 3.9.x**（非 4.x）的专用 Windows 机器上，按 README 第 6.4 节逐项通过「状态/会话/读消息/发文本/长文本分段/发文件/监听」验收，并确认锁屏、RDP 断开、显示缩放 100%、窗口不最小化、更新已阻断，之后才能接入上游。

## 7. 已知风险 / 后续

- **wxauto 兼容性**：仅支持微信 3.9.x；底层仍依赖 UIA。历史断点记录微信 3.9.11 聊天区为 `MMUIRenderSubWindow`，`uiautomation` 找不到 `EditControl`。wxauto 是否在该小版本可用必须目标机实测；若失败，不要硬上线，回到 `docs/handoff/checkpoints/T-11.md` 的坐标/视觉方案重新评估。
- **微信自动更新**：会直接升级到 4.x 导致不可用；README 8.2 给出锁版本/阻断更新步骤，需在目标机落实并每日巡检 `wechat_version`。
- **真实模式无业务幂等**：上游重试可能重复发送；建议上游只在网络错误时重试并限制次数。
- **memory/list 语义**：真实模式是当前会话列表，不是完整通讯录；`wxid` 可能为 null。
- **监听列表不持久化**：进程重启后需上游重新调用 `listen-list`。
- **服务化限制**：Windows 服务在 Session 0，无法操作交互式微信窗口；真实模式必须用计划任务「登录时」运行，nssm 仅建议 Mock。
- **待补**：在目标机安装 wxauto 后，跑一遍真实模式 smoke；若 wxauto 版本 API 有差异（如 `SendMsg` 签名），按 `wechat_ui.py` 中已有的 `_supports_kwarg` 兼容层调整。
