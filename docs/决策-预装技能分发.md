# 决策：原版 11 个预装技能是否随包分发

日期：2026-11-05　决策人：dsh-lead（建议）／待老板确认
关联：T-10（blocked:human）、docs/assets-inventory.md

## 结论（我的立场）

**不随包分发原版 .pyc 技能**，与 Codex 的"不推荐使用"一致；但**不是全部丢弃**，按来源分三类处理：

| 类别 | 技能 | 处置 |
|---|---|---|
| 原版自研（无授权声明、编译字节码） | agent-tool-box、douyin-automation、multi-platform-publish、wechat-mp-agent、tavily-search、self-improving-agent、find-skills | **不随包**。改为"用户自装/我们明文重写能力" |
| Anthropic 官方技能（带 LICENSE.txt） | pdf、xlsx、docx、pptx | 可随包（需按 LICENSE.txt 保留声明），体积小、纯本地文档处理，无平台风险 |
| 我们自己的资产 | 17 个员工技能（SKILL.md 明文） | 随包（已由代码实现：workspace-assets.ts） |

## 依据（均为实测证据）

1. **没有任何授权文本**。`resources/resources/preinstalled-skills/` 下 11 个目录里，只有 docx/pdf/pptx/xlsx 各有一个 LICENSE.txt；上面 7 个**一个都没有**。没有 LICENSE 不等于公有领域，默认是"保留所有权利"。
2. **没有源码，无法审计**。56 个 .pyc + 53 个 .py；.pyc 头四字节实测 `cb 0d 0d 0a`，即 **CPython 3.13 字节码**（magic 3531）。这意味着：绑定解释器小版本、我们改不了 bug、也无法证明里面没有上报/后门代码。把不可审计的字节码装进客户电脑，风险是单向的。
3. **合规风险会转移到我们身上**。douyin-automation（27 文件）、wechat-mp-agent、multi-platform-publish 属于"平台自动化发布/抓取"，抖音、微信公众平台的用户协议都禁止未经授权的自动化操作。原版随包分发时，风险由原厂承担；我们复刻后随包分发，**出事第一责任人是我们的公司主体**（中科元晟）。这不是技术问题，是法律与账号封禁风险。
4. **打包与维护成本**。要跑这些技能得随包 CPython 3.13 + 依赖（数百 MB），安装包从 128MB 涨到 500MB+；每次技能更新都要重发整包，而原版是靠 asar 热更新的。
5. **收益有限**。agent-tool-box 的 48 个工作流里，我们真正需要的是"私域/销售/新媒体"那几条；这些完全可以用明文的 17 个员工技能 + 服务端 API 覆盖。抓取类能力（抖音/小红书）本身就不稳定，随包也无法保证可用。

## 替代方案（按推荐顺序）

**A. 明文本地能力（推荐，1–2 人日/能力）**
把我们真正要用的 8–10 个原子能力用 Node/TS 重写，走官方接口或本地工具，不注入客户端：
- 飞书多维表格 → 已决定不用飞书，换本地表（已完成 33 表裁剪）
- 微信自动化 → 已定为自研 UI Automation（T-11）
- 抖音/小红书数据 → 只做"用户手动导出 + 我们解析"，不做自动抓取
- 公众号发布 → 调官方草稿箱 API（需公众号授权）

**B. 用户自装（0 成本兜底）**
技能目录里保留"可选依赖检测"：运行时若检测到 `python tool_box.py` 存在则调用，不存在则提示用户自行安装并给出官方购买链接。责任边界清晰：装在用户机器上、由用户自己获取。

**C. 商业授权（不现实）**
向原厂采购分发许可。周期与成本都不可控，不建议在首版阻塞。
