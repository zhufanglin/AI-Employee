# P21 存量重复记忆清理（memory_dedupe）

> 上线时间：2026-11-08 17:28（生产 47.85.46.165，dist 备份 `dist.bak.20261108172839`）
> 验证：本地单测 26 项 + 全量 VERIFY GREEN + 生产验收 14 项 GREEN

## 1. 为什么做

P20 给 `memory_save` 加了写入前查重，但它只管「以后」：

- P18/P19 验收、早期员工任务写下的记忆里，同一件事可能躺着 2–3 条；
- 用户 A 早期手工让员工「记住这个客户」，过几天又换个说法说了一遍，两条都在；
- 这些重复会让 `memory_search` 的返回里出现多份近似内容，模型容易把同一事实重复引用、甚至互相矛盾。

P21 提供一次性、可重复运行的清理工具，把存量收一遍。

## 2. 方案

三步，全部在服务端一次调用内完成：

| 步骤 | 做什么 | 为什么这么做 |
| --- | --- | --- |
| 粗筛（纯 JS） | 读该用户最近 200 条记忆，对每条算词面相似度（空格/标点切分 + 中文二元组，Jaccard），只把 `score ≥ 0.12 且 shared ≥ 2` 的前 5 条当候选 | 几百条记忆两两交给模型会把上游打爆；词面粗筛先挡掉 90% 无关记录，成本降到每条记忆最多 1 次模型调用 |
| 精判（小模型） | 复用 P20 的 `judgeMemory`（`doubao-seed-2.0-mini` + 关思考 + 8s 超时）：duplicate=同义重复 / merge=同主题补事实（给出合并正文）/ different=不同的事 | 词面相似不等于语义重复（「报价含税」和「税费另计」词面很近但结论相反），必须让模型定夺 |
| 落库 | `mode=apply` 时：合并进**较早**那条（id 不变、正文取合并结果、标签并集、命中次数相加），删除较晚那条；`mode=report` 只出报告 | 保留较早那条：客户偏好/报价往往越早越权威，后来的记录多为补充；外部引用早期 id 的概率也更高 |

预算保护：单次最多 `limit` 条（默认 30、上限 60）、最多 30 次模型调用、总耗时 55 秒；超了返回 `truncated=true`，再跑一次即可继续（apply 后记忆变少，天然收敛）。

## 3. 能力契约

能力名 `memory_dedupe`，分类 `memory`，JWT 鉴权（`POST /api/capabilities/run`）。

| 参数 | 说明 |
| --- | --- |
| `mode` | `report`（默认，只报告不改数据）\| `apply`（执行合并与删除） |
| `limit` | 本次扫描多少条（从最新往回扫），默认 30，最多 60 |

返回：

```json
{
  "mode": "report",
  "total": 200,          // 该用户记忆总数（最多取 200）
  "scanned": 30,         // 本次参与扫描的条数
  "calls": 3,            // 实际调用模型的次数
  "applied": 0,          // apply 模式下实际执行的合并数
  "truncated": false,    // 是否因次数/耗时上限提前结束
  "durationMs": 3429,
  "proposals": [
    {
      "relation": "merge",             // merge（合并）| duplicate（重复）
      "keepId": "cmw...", "dropId": "cmw...",
      "keepTitle": "...", "dropTitle": "...",
      "keepCreatedAt": "...", "dropCreatedAt": "...",
      "similarity": 0.348,             // 词面相似度，便于人工复核
      "mergedPreview": "合并后的正文（前 200 字）"
    }
  ]
}
```

**为什么不放进执行器（`packages/worker/tool-loop.mjs` 的 CAPABILITIES）**：这是破坏性运维操作（会删除记忆）。员工在执行任务时不应该自己被授予「批量删记忆」的能力；它只对「用户自己的 JWT」开放，由人（或运维脚本）显式触发。

## 4. 怎么用

运维脚本 `scripts/run-memory-dedupe.mjs`（自动短信登录，白名单手机号直接拿 devCode）：

```bash
# 1) 先看报告（默认，不改数据）
node scripts/run-memory-dedupe.mjs

# 2) 确认后执行
node scripts/run-memory-dedupe.mjs --mode=apply

# 生产（在 47.85.46.165 上）
/opt/node/bin/node --dns-result-order=ipv4first run-memory-dedupe.mjs --mode=report --limit=60
```

输出示例：

## 7. 踩过的坑

1. **报告模式要把 keep 和 drop 都标记为已处理**，否则同一条既当保留方又当被合并方，报告里会出现互相重叠的建议。
2. **粗筛阈值不能只看相似度**：两个短句（「直播排期」/「开票抬头」）可能因为一个共同二元组就超过 0.12，所以要求 `shared ≥ 2`。
3. **合并后要更新内存里的 keep 行**（`keep.content = nextContent`），否则同一轮后续比对看到的还是旧正文，可能把刚合并进来的事实判成 different。
4. **模型判定失败时日志文案是「按新增写入」**（复用 P20 `judgeMemory` 的日志），在清理场景语义上应是「跳过这条」，只影响日志可读性，不影响数据安全（失败一律不删不改）。
5. **apply 会删除数据且没有恢复接口**：生产上先跑 report 人工看一遍是硬性流程；`dist` 与数据库都有每日备份（`/opt/fcmediaagent/app/dist.bak.*`、MySQL 容器数据卷）。
6. 生产验收里 report/apply 各扫一遍会重复调用模型——这是刻意的：apply 必须基于「此刻的数据」重新判定，不能直接复用 report 的结论（间隔里可能有新写入）。

## 8. 还没做

- **定时自动清理**：目前要人工/脚本触发。可以接 cron（服务端已有 `EmployeeCron`，但那是员工任务，不是内部维护任务），建议等记忆量真正变大（>1000 条/用户）再上。
- **桌面端入口**：现在只能通过 API/脚本跑，后台还没有「记忆管理」页面。
- **按 kind / 时间范围过滤**：现在一次扫最新 N 条，不能只清「preference 类」或「上个月之前的」。
- **撤回**：apply 前不落快照，只有数据库备份兜底。
