## 0. 一句话结论（先看这个）

原版**没有**「让用户填两张表喂给模型」的产品设计，它实际是：

1. **战略 = 一份飞书在线文档（10 节长文，模板 625 行）+ 一张「战略表」只存版本迭代记录**。战略文档全文在运行时才被 workflow 用飞书 API 拉取，**截断到 6000 字**后拼进那一次 LLM 调用的 prompt，**不是常驻 system prompt**。【原文】`BT\字段.md:10`+`V2\战略方向文档_模板.md:1-623`【pyc】`TB\utils\soul_strategy_reader.pyc`
2. **人设 = 一张「人设规划表」，8 个字段，一个账号一行**。它**只被流量/内容/数据三条链路读取**（爆款文案生成、每日方向分析、账号运营档案），拼进文案生成 prompt 和选题 8 维打分的 persona 维度。【原文】`BT\bitable_config.json:252-265`【pyc】`TB\capabilities\workflows\traffic_flows.pyc`
3. **员工的「岗位知识」全部写死在 15 份 SOUL.md 模板里**（每份 12-45KB，含职责、表契约、workflow 编排、红线）。战略/人设是**数据面**，SOUL 是**岗位面**，两者是「岗位技能 + 数据叠加」，不是「员工读战略自己拆活」。
4. 客户端里**根本没有战略/人设的表单**：唯一的入口是教程第 4 步按钮「编辑战略文档」（打开飞书 docx 让用户自己写）和「一键创建」向导（自动建表 + 注入 SOUL）。**「训练 / 喂养 / 语料」在渲染层 0 命中** —— 原版不存在「员工训练」功能。
5. 所谓的「知识库」是另一套东西：独立的 RAG 检索（硅基流动 embedding + top_k），服务于聊天检索注入，与战略/人设无关。

## 5. 与原版 12（实为 14 个注册角色）名员工技能的关系

### 5.1 结论：**不是「读战略表自己拆活」，是「岗位技能 + 战略/人设数据叠加」**

原版员工的能力 = 三层叠加，缺一层就跑不动：

```
第 1 层  岗位 SOUL.md（15 份模板，每份 12-45KB）
        = 身份 + 职责 + 「输入源表」（我该读哪几张飞书表）+ workflow 调用方式 + 绝对红线
第 2 层  共享数据表（战略文档 / 战略表 / KPI 表 / 人设规划表 / 每日内容更新方向表）
        = 运行时被 workflow 读出来，拼进 user_prompt
第 3 层  技能底座 3 个（agent-tool-box 41 原子能力 + 62 workflow、douyin-automation、wxauto + wechat-mp-agent）
        = 真正干活的 Python 代码
```

**关键证据：拆活是 workflow 代码写死的，不是 LLM 现场规划。** 【原文】`V2\爆款内容策略官_SOUL.md:135` 逐字：

> 「本模块已由 `traffic_generate_copy_workflow` 完整实现，workflow 内部自动编排以下步骤，agent 无需手动逐步调用。」

即：LLM/agent 在链路里的角色是「写文案 / 做分析 / 出汇总」，**流程步骤是 Python 写死的**，不是 agent 读战略后自己拆解任务。CEO 是唯一的例外——它确实「读战略 → 拆今日任务 → 通过 `sessions_send` 分派」，但拆解模板也是写在 SOUL 的固定协议里（【原文】`V2\CEO_SOUL.md:144` 「## 团队指挥调度协议（v2.2）」）。

## 6. 复刻建议（NestJS + Electron + 17 个 SKILL.md + workspace 文件 + tool-loop.mjs）

### 6.1 现状差距（先认清我们缺什么）

| 原版 | 复刻版现状 | 差距 |
|---|---|---|
| 战略文档 6000 字，按节切片，运行时拉取 | `packages/worker/tool-loop.mjs:4` 的 `INSTRUCTIONS` 只有一句「工作区有没有『企业基础资料.md』『客户资料』，有就读进来」 | **没有结构化档案，也没有注入通道**；靠模型自己想起来读文件，不可靠 |
| 每份 SOUL 声明输入源 | 17 个 `boss-*` SKILL.md 无「我需要哪些数据」声明 | 无法按需注入 |
| 人设表 8 字段 | `schema.prisma:557` `CustomerProfile` 是客户档案，非 IP 人设 | **缺 IP 人设模型** |
| 战略版本表 13 字段 | `schema.prisma:581` `StrategySummary` 只有 id/phone/name/content | 只是「战略汇总文本」，**无版本号/迭代记录** |
| 注入用 workflow 拼 user_prompt | `tool-loop.mjs:80` 固定 `[{role:"system",content:INSTRUCTIONS}, ...messages]` | 注入只能改 system，需要新拼装点 |

### 6.2 建议的字段设计（**12 个字段就够，别照抄 13**）

原版战略表 13 字段里有 4 个是「管理流程装饰」（参考数据/预期效果/实际效果/落地执行表），复刻取核心：

```
需要保留的 8 个：版本号 / 版本类型 / 迭代日期 / 触发原因 / 变更板块 / 变更摘要 / 变更人 / 文档链接
可以砍掉的 5 个：参考数据、预期效果、实际效果、KPI表、落地执行表
  → 理由：前 3 个一线不用；KPI表 在复刻版是独立 KPI 概念，无需外链字段；
    落地执行表 在原版 36 张表里根本不存在（见 §7），是死字段。
```

人设表照抄 8 字段即可（日期/名称/人设规划/定位/创建时间/所属账号/粉丝量/主页链接），其中 `人设规划` + `定位` 是 **自由长文本**，别拆成结构化选项——原版就是靠 `_derive_objective` 和 2 字滑窗词元硬啃自由文本的，拆细了反而限制表达。

### 6.3 存储位置：**工作区文件为主，Prisma 只存索引**（关键取舍）

| 数据 | 建议存储 | 理由 |
|---|---|---|
| 战略正文（6000 字级长文） | `workspace/{phone}/企业战略.md`，带 front-matter（`version` / `updated` / `owner`） | ① 复刻版 agent 已有 `file_read`，零成本可读 ② 用户可直接用记事本改，符合「老板自己填表」的直觉 ③ 不必为长文本建表 |
| 战略版本记录 | Prisma 新表 `StrategyIteration` | 需要按版本查/回滚，文件不适合 |
| 人设 | Prisma 新表 `PersonaProfile`（或复用工作区 `账号人设.md` 首版） | 一账号一行，天然是表；但首版人数少，文件也能撑 |
| 注入用的缓存 | 内存 + TTL 300s（照抄原版 `_strategy_cache`） | 避免每轮读盘 |

Prisma 迁移草案（**首版只加 2 张表**）：

```prisma
model StrategyDoc {          // 单行/租户，正文落文件时此表只存指针与元信息
  id        String   @id @default(cuid())
  phone     String
  version   String   @default("V1.0")
  filePath  String                       // workspace/{phone}/企业战略.md
  updatedBy String?
  updatedAt DateTime @updatedAt
  @@unique([phone])
}

model StrategyIteration {    // 对应原版「战略表」13→8 字段
  id          String   @id @default(cuid())
  phone       String
  versionNo   String                     // 版本号
  versionType String   @default("微调")   // 重大迭代 | 微调
  iteratedAt  DateTime                   // 迭代日期
  trigger     String                     // 触发原因
  sections    String?                    // 变更板块，JSON 数组字符串
  summary     String                     // 变更摘要
  author      String?                    // 变更人
  docUrl      String?                    // 文档链接
  createdAt   DateTime @default(now())
  @@index([phone, versionNo])
}

model PersonaProfile {       // 对应原版「人设规划表」8 字段
  id          String   @id @default(cuid())
  phone       String
  name        String                     // 名称 = 账号/IP 名
  positioning String?                    // 定位
  plan        String   @db.MediumText    // 人设规划（自由长文本）
  accountId   String?                    // 所属账号
  followers   String?                    // 粉丝量（原版是 TEXT）
  homepage    String?                    // 主页链接
  effectiveAt DateTime                   // 日期
  createdAt   DateTime @default(now())
  @@index([phone, name])
}
```

### 6.4 注入点：改 `tool-loop.mjs` 的三处（**不要塞进 INSTRUCTIONS 常量**）

现状（`packages/worker/tool-loop.mjs`）：

```
:80  const transcript = [{ role: "system", content: INSTRUCTIONS }, ...messages];
:91  transcript[0].content += "\n能力参数说明：" + JSON.stringify(caps).slice(0, 12000);
:92  const section = skillSection(skill);           // :50-55，截 SKILL_BUDGET=8000
:93  if (section) transcript[0].content += section;
```

**建议注入顺序（严格照此，越靠后权重越高）**：

```
INSTRUCTIONS（通用规矩）
→ 能力参数说明（现有）
→ 【新增】## 当前员工岗位的数据授权    ← 解析 SKILL.md front-matter 的 needs
→ skillSection（岗位 SKILL.md，8000 预算）
→ 【新增】## 公司战略（当前版本 {version}，更新于 {updated}）  ← 切片 ≤6000 字
→ 【新增】## 账号人设（仅声明 needs 人设的岗位）              ← ≤1500 字
```

理由：原版把战略放在 user_prompt（更靠后），复刻版若只能改 system，就放在 **skillSection 之后**——即整段 system 的最尾部，等价于「最贴近 user 的约束」，最不容易被 SKILL.md 的通用说明冲淡。

**按需注入（照抄原版「输入源表」）**：给 17 个 `boss-*` SKILL.md 加 front-matter：

```yaml
---
name: boss-daily-lead-topics
needs: [strategy.sections:服务客户人群,产品体系]   # 只要这两节，不取全文
---
```

worker 侧解析 `needs`，只取对应节 → **同一个岗位只吃它该吃的 3-5KB，而不是全员 6000 字**。这是原版 `read_strategy_section` / `read_channel_persona_text` 的等价物。

### 6.5 迁移顺序（4 步，每步都可独立上线）

| 步 | 内容 | 产出 | 风险 |
|---|---|---|---|
| ① 建通道 | 工作区 `企业战略.md` 模板 + `tool-loop.mjs` 注入函数（含 6000 截断、TTL 缓存、文件缺失时静默跳过） | 员工能「看到」战略，但还没有 UI | 低；文件不存在则行为不变 |
| ② 加声明 | 17 个 SKILL.md 补 front-matter `needs`，worker 按需切片 | 每岗位只吃相关节 | 低 |
| ③ 加人设 | `PersonaProfile` 表 + 人设注入（仅 6 个流量/内容类岗位） | 文案链路可用人设 | 中（涉及文案生成 prompt） |
| ④ 加版本 | `StrategyDoc` + `StrategyIteration` + 「保存即追加迭代记录」 | 可追溯改了什么 | 低 |

**不要一上来就做 9 中心 36 张表的飞书多维表格复刻**——原版的飞书是为了「多人协作 + 老板手机上也能看」，复刻版是单机单租户，这套复杂度换不来等价价值。

### 6.6 五条明确取舍（请 lead 决策）

1. **战略存文件，不存 Prisma 长文本列。** 理由：`file_read` 已存在、用户可手改、可版本 diff；Prisma 只存 `version/updatedAt` 指针。原版之所以进飞书文档，是因为要多人协作；我们没这个约束。
2. **注入按节，不注全文。** 原版 `read_strategy_section` + `read_channel_persona_text` 已证明「全文 6000 字塞所有岗位」是浪费；复刻用 SKILL.md front-matter 声明 `needs`，单岗位 3-5KB 足够。
3. **不做「员工训练/喂养/语料」界面。** 已用全量字符串扫描证明原版也没有（见 §7），老板记忆里的「训练」其实=**填战略文档 + 填人设表 + 知识库 RAG** 三件事的组合观感。做训练界面属于自创需求。
4. **人设只给 6 个岗位，不给全员。** 原版证据显示只有爆款情报官/爆款内容策略官/账号运营官/数据分析师/流量操盘手/新媒体运营消费人设；把 IP 人设注入销售/客服的 system 只会污染话术。
5. **首版只加 2 张表（`StrategyIteration` + `PersonaProfile`），复用现有 `StrategySummary` 作为「战略摘要缓存」。** `schema.prisma:581` 的 `StrategySummary` 语义其实等同于原版 CEO 工作流写进战略表的「战略汇总（200 字）」，把它当缓存行留着，别删。
