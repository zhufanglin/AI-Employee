# P19 记忆语义检索（memory_search 升级）

> 上线日期：2026-11-08　状态：**已上线生产**（生产验收 12 项 GREEN）
> 相关能力：`memory_save` / `memory_search` / `memory_list` / `memory_delete`（P18 落地，P19 把 search 升级为语义检索）

## 1. 为什么做

P18 的 `memory_search` 是纯字面检索（MySQL LIKE + 关键词打分）。老板/员工提问时的用词和当初记录时的用词经常不一致：

| 用户问 | 记忆里其实这么写的 | P18 结果 | P19 结果 |
| --- | --- | --- | --- |
| 这个客户价格是怎么收的 | 报价必须含税 | 靠「客户」勉强命中，排序靠后 | 命中，语义分 75–88 |
| 他那边结汇走什么渠道 | 回款走 Payoneer | **0 条** | 排名第 1（语义分 90） |

## 2. 方案选型：为什么不用 embedding

1. 2026-11-07 实测火山方舟 `POST {ARK_BASE_URL}/embeddings` 对当前账号全部 404：
   `doubao-embedding-large-text-250515`、`doubao-embedding-text-240715`、`doubao-embedding-large-text-240915`、
   `doubao-embedding-250615`、`doubao-embedding-large-250615`、`doubao-embedding-text-250515`
   均返回 `InvalidEndpointOrModel.NotFound`（The model or endpoint … does not exist or you do not have access to it）。
2. 生产 `.env` 里没有任何 SiliconFlow / DashScope 之类的 embedding 凭证。
3. 本地跑 onnx embedding 要往 4C8G 的生产机塞 200MB 依赖，还要为历史记忆批量补向量。
4. 单用户的记忆量只有几百条，**不建向量索引也能靠「小模型扩展 + 小模型重排」做出语义效果**。

于是采用三步检索，全部走小模型 `doubao-seed-2.0-mini`（别名已在 `ALIAS_MAP` 注册）：

```
query ──①扩展──> 6 个同义/口语关键词 ──②LIKE 召回 + 候选补齐──> 最多 15 条 ──③模型重排 0–100──> 加权合并 → 排序
```

- **① 查询扩展**（`expandQuery`）：把「这个客户价格怎么收」扩成 报价 / 收费 / 费用 / 收费方式…
  提示词要求「每个词 2-6 字、不带这个/那个/客户这类泛指前缀」，否则会得到「客户报价」「客户价格」这种带噪音的词。
  带 10 分钟 TTL 缓存（上限 300 条），同一句重复查询不再打模型。
- **② 召回 + 补齐**：扩展词只解决「词不同」，纯语义表述（结汇 ↔ 回款）照样 LIKE 不到，
  所以候选不足 15 条时用**最近的 60 条记忆**把候选位补满，交给重排去挑。
- **③ 重排**（`rerank`）：一次把最多 15 条候选（正文截 120 字）交给模型打 0–100，分档
  0=无关 / 1-30 弱相关 / 31-70 部分相关 / 71-100 直接回答。
- **合并**：`归一化关键词分 × 0.4 + 语义分 × 0.6`；没有语义分（模型失败/关掉）时等于纯关键词排序。
  补齐进来的条目关键词分为 0，只能靠语义分进榜。

## 3. 性能实测（这是本次最大的坑）

`doubao-seed-2-0-lite-260428` **默认开思考**（响应带 `reasoning_content`，`usage.completion_tokens_details.reasoning_tokens` 上千），
一次检索 20–40 秒，微信客户根本等不起：

| 场景 | 开思考 | 加 `thinking:{type:"disabled"}` |
| --- | --- | --- |
| 查询扩展（lite） | 7217ms | 5725ms（mini 755–1564ms） |
| 重排 2 条 | 19239ms（1166 reasoning tokens） | — |
| 重排 10 条 | 38870ms（2428 reasoning tokens） | **1655ms（mini）/ 2802ms（lite）** |
| 重排 30 条 | 33431ms，且分数退化成 0/30 粗值 | 未采用（上限 15 条） |
| 生产一次完整语义检索 | 15029ms（撞 8–15s 超时 → 退化为纯关键词） | **1.0–3.1s** |

结论：`LLM_TIMEOUT_MS` 从 15000 收到 **8000**，候选从 40 收到 **15**，正文从 200 字收到 **120 字**，
每次调用都带 `thinking: { type: "disabled" }`。

## 4. 能力契约

`memory_search` 入参：

| 参数 | 说明 |
| --- | --- |
| `query` | 必填，自然语言提问即可（≤200 字） |
| `limit` | 1–20，默认 5 |
| `mode` | `auto`（默认，语义）/ `keyword`（强制纯字面，不调模型） |

出参新增：`expandedTerms`（扩展出来的词）、`semantic`（本次是否真的用上了语义分），
每条 item 新增 `keywordScore` / `semanticScore`（`semanticScore: null` 表示没参与语义）。

环境变量：`MEMORY_SEMANTIC=0` 全局关掉语义；`MEMORY_SEMANTIC_MODEL` 覆盖模型别名（默认 `doubao-seed-2.0-mini`）。

## 7. 踩过的坑

1. **推理模型不能直接用于检索链路**：lite 默认开思考，重排 10 条要 38.9s。必须 `thinking:{type:"disabled"}`，
   并换更快的 mini；否则表现是「稳定撞超时 → semantic=false → 静默退化成纯关键词」，看起来只是「不生效」。
2. **`ALIAS_MAP` 里没注册的别名会静默回落到 `DEFAULT_UPSTREAM_MODEL`（pro，更慢更贵）**，
   不报错。新增小模型要先加 `ALIAS_MAP` 条目。
3. **只做扩展 + LIKE 召回不算语义**：扩展词仍是「词」，遇到同义改写（结汇 ↔ 回款走 Payoneer）召回为 0，
   重排连候选都没有。必须有「候选补齐」这一步。
4. **候选给太多反而更差**：30 条时分数退化成 0/30 的粗值，还慢；15 条是质量与延迟的折中。
5. 生产机上探针脚本要带 `--dns-result-order=ipv4first`，否则 Node 先试 IPv6 直接 ETIMEDOUT（生产无 IPv6 路由）。

## 8. 还没做

- 记忆量上千条后「补齐候选只看最近 60 条」会漏掉老记忆，届时需要真正的向量检索（等 embedding 凭证）或分页重排。
- 目前只对单次检索做重排，没有做「多轮追问上下文」的检索改写。
- 记忆没有自动去重/合并，同类偏好写多了会重复占候选位。
