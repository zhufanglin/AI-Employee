## 2. A：MySQL + uploads 备份

### 2.1 改了什么

`scripts/ops/backup-prod.sh` 保留原 MySQL 逻辑，新增：

- 新变量：
  - `UPLOADS_DIR`，默认 `/opt/fcmediaagent/app/uploads`
  - `UPLOADS_BACKUP_DIR`，默认 `/opt/fcmediaagent/backups/uploads`
- 归档命令：
  ```bash
  tar --warning=no-file-changed -czf "<UPLOADS_BACKUP_DIR>/uploads-<TS>.tar.gz.partial" -C "<UPLOADS_DIR>" .
  ```
  - `-C ... .` 会包含 uploads 下的隐藏文件，保持相对路径。
  - `--warning=no-file-changed` 只降低“归档时文件正在变化”的噪音，不掩盖真正错误。
  - 目录不存在：只打印“跳过 uploads 归档”，不视为失败。
  - 目录存在但不可读：预检直接失败，避免“备份成功但 uploads 是空的”。
  - `tar` 返回 1（归档期间文件变化）且 `gzip -t` 通过时，警告后继续；其他非 0 直接失败。
  - 归档后先写 `.partial`，`gzip -t` 校验通过、非空，再 `mv` 成正式文件；失败会清理 `.partial`。
  - 生成 `uploads-<TS>.tar.gz.sha256`，日志打印文件大小、字节数、sha256 和校验命令。
- 保留策略：沿用 `RETENTION_DAYS`（默认 14）。`prune_old_uploads()` 用 `find ... -mtime +(RETENTION_DAYS-1)` 删除过期 `uploads-*.tar.gz` 及其 `.sha256`。
- OSS 异地备份：
  - 原来只上传 MySQL 包；现在 `OSS_UPLOAD=1`（或 `--oss`）时分别上传：
    - MySQL：`--prefix backups/mysql`
    - uploads：`--prefix backups/uploads`
  - 上传调用 `/opt/fcmediaagent/ops/oss-upload.mjs`；凭据由该脚本从 `/opt/fcmediaagent/app/.env` 读取 `OSS_*`，**不打印值**。
  - 单个包上传失败只写“警告”，本地备份仍判成功；本地归档失败才会让整次备份退出 1。
- `--dry-run`：
  - 关闭 `LOG_FILE`，真正只打印、不写 `backup.log`、不调用 `docker`/`tar`、不写任何备份文件。
  - 打印 MySQL、uploads、OSS 的计划；uploads 目录不存在时打印跳过原因。
- 失败语义：预检/导出/归档/校验/清理失败退出 1；参数错误退出 2。systemd 会记录失败，且 `Restart=no`，次日 timer 再跑。

> 注意：`restore-prod.sh` 目前仍只恢复 MySQL，**不自动恢复 uploads**。灾难恢复时 uploads 需要手工解包（见 2.4）。这是本次范围外的已知缺口，不要在恢复演练里假设它已自动化。

### 2.2 为什么

- 之前只有 MySQL，用户工作区与交付件（`/opt/fcmediaagent/app/uploads`）丢失后无法从备份恢复。
- 没有异地备份，机器/磁盘整体故障时本地备份一起丢；OSS 是现成的异地存储。
- uploads 是用户文件，可能出现“归档时正在上传/删除”，所以既要容错 tar=1，又要用 `gzip -t` 防止坏包。
- dry-run 必须真的“只打印”，否则在非生产机或排障时会偷偷写日志/文件。

## 3. B：systemd 备份单元

### 3.1 改了什么

`ops/systemd/fcmediaagent-backup.service`：

```ini
Environment=RETENTION_DAYS=14
Environment=OSS_UPLOAD=1
EnvironmentFile=-/etc/default/fcmediaagent-backup
```

- `OSS_UPLOAD=1` 默认启用，开机/每次 timer 触发都生效。
- `EnvironmentFile` 放在 `Environment=` 之后，systemd 后者覆盖前者；因此在 `/etc/default/fcmediaagent-backup` 写 `OSS_UPLOAD=0` 即可临时关闭，不用改 unit。
- `EnvironmentFile` 前的 `-` 表示文件不存在也不报错。
- 其余保留：`User=root`、`TimeoutStartSec=3600`、`Nice=10`、`IOSchedulingClass=idle`、`Restart=no`。
- `fcmediaagent-backup.timer` 只改描述，调度仍是每天 03:30 + 最多 5 分钟随机延迟 + `Persistent=true`。

### 3.2 为什么

- OSS 异地备份要默认开启，否则“配了 OSS 凭证但没人记得加 --oss”会继续没有异地备份。
- 保留 `/etc/default` 覆盖，运维临时关闭不用改仓库/unit，也不会在下次下发时被覆盖。

### 3.3 生产怎么下发

```bash
scp -i "$KEY" ops/systemd/fcmediaagent-backup.service ops/systemd/fcmediaagent-backup.timer "$PROD:$STAGE/"

ssh -i "$KEY" "$PROD" '
  set -e
  TS=$(date +%Y%m%d-%H%M%S)
  for f in fcmediaagent-backup.service fcmediaagent-backup.timer; do
    [ -f /etc/systemd/system/$f ] && cp -a /etc/systemd/system/$f /root/$f.bak-$TS || true
  done
  install -m 0644 /tmp/p49-ops/fcmediaagent-backup.service /etc/systemd/system/fcmediaagent-backup.service
  install -m 0644 /tmp/p49-ops/fcmediaagent-backup.timer   /etc/systemd/system/fcmediaagent-backup.timer
  systemctl daemon-reload
  systemctl restart fcmediaagent-backup.timer
  systemctl enable fcmediaagent-backup.timer
'
```

> 不要在没确认 OSS 凭证前直接 `systemctl start fcmediaagent-backup.service`；真实备份会跑 MySQL dump + uploads 归档，并尝试上传。

### 3.4 怎么验证

```bash
ssh -i "$KEY" "$PROD" '
  systemctl cat fcmediaagent-backup.service | grep -E "Environment|ExecStart"
  systemctl show fcmediaagent-backup.service -p Environment
  systemctl list-timers fcmediaagent-backup.timer --no-pager
  systemctl status fcmediaagent-backup.timer --no-pager

```

期望：`Environment` 中含 `OSS_UPLOAD=1`；timer 显示下一次 03:30 左右触发。手动触发一次用 `systemctl start fcmediaagent-backup.service`，再用 2.4 的方法验证产物。

## 4. C：监控告警 webhook

### 4.1 改了什么

`scripts/ops/monitor.mjs` 的 webhook 取值改为四级优先级：

1. 进程环境变量 `ALERT_WEBHOOK_URL`（最高）
2. `/etc/default/fcmediaagent-monitor` 里的同名项（systemd 通过 `EnvironmentFile=-/etc/default/fcmediaagent-monitor` 注入；脚本也主动读该文件，兼容手工执行）
3. 配置文件 `alert.webhookUrl`（`monitor.config.example.json` 里已有说明）
4. `/opt/fcmediaagent/app/.env` 里的同名项（最后兜底）

无 webhook 时，日志明确输出：

```text
[monitor] 有 N 项待推送，未配置 ALERT_WEBHOOK_URL，告警仅写本地日志（可写入 /etc/default/fcmediaagent-monitor，参考 ops/README.md）
```

- 零新增外部依赖，仍只用 Node 内置 `fs`/`fetch`。
- 推送目标按 URL 自动识别：钉钉、飞书、企业微信（与原有实现一致）。
- 同一检查有冷却期，恢复时推一次“已恢复”；这些逻辑未改。

### 4.2 为什么

- 之前有外推能力但缺配置时静默，告警只落本地日志，没人知道。
- 把配置放在 `/etc/default/fcmediaagent-monitor`，权限 0600，避免 webhook（含 token）混进 `app/.env` 或仓库。
- 环境变量优先，便于临时排障覆盖；文件兜底，便于 systemd 与手工执行一致。

## 5. D：生产回归 sms_login 去 devCode 化

### 5.1 改了什么

`scripts/ops/prod-regression.mjs` 的 `sms_login` 检查不再：

- 调用 `POST /api/auth/sms/send`；
- 读取响应里的 `devCode`；
- 依赖 `/opt/fcmediaagent/app/.env` 的 `DEV_SMS_ALLOWLIST`。

新流程：

1. 取测试号：默认 `13900000002`，可用 `--phone` 覆盖；校验 `/^1[3-9]\d{9}$/`。
2. 读取 `--env-file`（默认 `/opt/fcmediaagent/app/.env`）里的 `DATABASE_URL`，解析 MySQL 用户/密码/库名/端口。
3. 通过 `child_process.execFileSync('docker', ...)` 在 `fcm-mysql` 内执行 mysql 客户端（容器名可用 `--container` 覆盖）。
4. 连接候选顺序：
   - `DATABASE_URL` 里的 app 用户，走容器内 TCP `127.0.0.1:3306`；
   - `docker exec fcm-mysql printenv MYSQL_ROOT_PASSWORD` 得到的 root 密码，走容器内 socket；
   - root 免密 socket（最后兜底）。
5. 先 `SELECT 1` 确认数据库可达；再 `SELECT COUNT(*) FROM \`User\` WHERE phone=...` 判断测试号是否已存在。
6. 插入一行 `VerificationCode`：
   ```sql
   INSERT INTO `VerificationCode`
     (`id`,`phone`,`code`,`purpose`,`expiresAt`,`used`,`createdAt`)
   VALUES
     ('<id>','<phone>','<6位code>','login',DATE_ADD(NOW(), INTERVAL 5 MINUTE),0,NOW());
   ```
   - `code` 为 `randomInt(0, 1000000)` 补零的 6 位；
   - `purpose='login'`，5 分钟内有效，`used=0`。
7. `POST /api/auth/sms/login`，body `{phone, code}`；只有测试号原本不存在时才追加 `consent: { version: '2026-11-12', source: 'prod-regression' }`（版本可用 `REGRESSION_CONSENT_VERSION` 覆盖），拿 `accessToken` 写回 `ctx.token`。

   - `ok: true`
   - `skipped: true`
   - 文案“短信登录检查已跳过（不判失败）：...”
   随后 `checkAuthed` 也因 `ctx.authSkipReason` 跳过，避免连带失败。`monitor.mjs` 只把 `ok === false` 判失败，所以 skip 不会让整轮回归 fail。

## 6. E：nginx 限流

### 6.1 改了什么

新增两个文件，**必须成对使用**：

1. `ops/nginx/fcmediaagent-ratelimit.conf`（**只能 http{}**）
   - `limit_req_zone $binary_remote_addr zone=fcm_auth:10m rate=5r/m;`
   - `limit_req_zone $binary_remote_addr zone=fcm_api:20m rate=30r/s;`
   - `limit_req_log_level warn;`
   - `upstream fcm_backend { server 127.0.0.1:3000; keepalive 32; }`
2. `ops/nginx/fcmediaagent-ratelimit-locations.conf`（**只能 server{}**）
   - `location ^~ /api/auth/sms`、`^~ /api/auth/login`、`^~ /api/auth/register`：
     `limit_req zone=fcm_auth burst=5 nodelay; limit_req_status 429;`
   - 其余 `location ^~ /api/`：`limit_req zone=fcm_api burst=30 nodelay; limit_req_status 429;`
   - 每个 location 都带 `proxy_pass http://fcm_backend`、Host/X-Real-IP/X-Forwarded-For/X-Forwarded-Proto、`Connection ""`、`proxy_buffering off`、长超时，沿用原生产站点的 SSE 语义。

为什么拆两个文件：nginx 的 `include` 是文本级拼接，`limit_req_zone` 是 http 级指令，不能出现在 `server{}`/`location{}`；一个文件不可能同时被 http{} 与 server{} 合法 include。拆开并在注释里标明上下文，避免运维放错位置导致 `nginx -t` 报 `limit_req_zone directive is not allowed here`。

### 6.2 为什么

- 登录/短信/注册无速率限制，可被暴力刷短信、撞库，产生费用与安全风险。
- 认证接口 5r/m + burst=5 对正常用户足够；其余 API 30r/s + burst=30 防止单 IP 打满。
- 用 `$binary_remote_addr` 不依赖 `X-Forwarded-For`，避免伪造头绕过；如果未来上 CDN，需要配合 `real_ip` 模块改成真实客户端 IP。

**然后按现场情况二选一**（必须人工编辑，不要盲目 include）：

#### 情况 1：站点里没有 `location /api/`、也没有上述三个认证 location

在 443 的 `server { ... }` 内加一行：

```nginx

```

#### 情况 2：站点里已有 `location /api/` 或认证 location

**不要 include 整个 locations 文件**（会 `duplicate location`）。只把对应两行合并进已有 location：

```nginx
limit_req zone=fcm_auth burst=5 nodelay;   # 仅 /api/auth/sms|login|register
limit_req_status 429;

limit_req zone=fcm_api burst=30 nodelay;   # 仅其余 /api/

```

原有 `proxy_pass`、超时、buffer 等全部保留；若原站点已有 `upstream` 且名称不是 `fcm_backend`，把 locations 文件里的 `proxy_pass` 改成原 upstream 名称，或删掉 http 片段里的 `upstream fcm_backend` 段复用原有的。

> 现场注意：
> - 生产站点 80/443 反代 `127.0.0.1:3000`，`client_max_body_size 220m`，并关闭 buffering 支持 SSE；这些是 P44 运维手册记录，实际以 `nginx -T` 为准。
> - 如果 80 只是 301 到 443，限流只需要在 443 server 生效；不要重复定义导致 80 也限流两次。
> - `^~` 前缀比正则 location 优先，可能绕过站点原有的正则规则；合并前先看 `nginx -T` 的 location 顺序。

- **测试手机号**：默认 `13900000002`；若生产已有专门测试号，下发时用 `--phone` 或在 unit 里加 `Environment=REGRESSION_PHONE=...`。
- **DEV_SMS_ALLOWLIST 代码层彻底删除**：本轮只摘生产 env；代码里的调试分支仍在 `packages/server/src`，需另开任务（涉及发布），不在本次范围。
- **restore-prod.sh 不支持 uploads**：本次只做备份；恢复演练需按 2.4 手工解包，后续可另开任务把 uploads 恢复纳入脚本。

### 8.4 风险与注意

- 备份会额外占用磁盘（uploads 包大小取决于用户文件量），预检有 <1GB 警告；首次上线后观察 `df -h` 与 `backups/uploads` 增长。
- OSS 上传失败不会让备份失败，所以“备份成功”不等于“异地成功”；看日志中的 `OSS 上传完成` 或 OSS 控制台。
- 限流 5r/m 对 NAT/办公网共享出口可能偏严；如误伤，调 `fcm_auth` 到 10r/m 或 burst=10，改完 `nginx -t && systemctl reload nginx`。
- 回归播种验证码是写库操作；虽然 5 分钟过期，仍应确认测试号策略与数据合规要求。
- 所有 `.env` 修改前先备份；不要把密钥贴到工单/聊天/日志。
