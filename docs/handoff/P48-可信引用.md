# P48 可信引用（来源核对 source_check）

## 1. 为什么做
- 用户问「这个来源核对是 AI 自己去核对吗」。原来的做法是让模型自己在正文里标「（来源：xx）」，等于模型自证，不可信。
- 用户拍板（m23677）：「要可信,请执行」。
- 结论：可信必须由**程序**给出证据，而不是模型的自我声明。

## 2. 三层判定
| 层 | 谁做 | 结论 |
| --- | --- | --- |
| 链接能不能打开 | 服务端 `web-extract`（含 SSRF 守卫） | `unreachable` |
| 页面里有没有这句原话 | 服务端 `quoteMatches`（归一化后比对） | `verified` / `quote-not-found` |
| 只有链接没有原句 | 服务端 | `reachable`（只能证明页面存在，不得当已核实） |

归一化 = NFKC（全角转半角）+ 去掉空白与中英文标点（含 % ％），所以「增长 131％」与「增长131%」算同一句；
先判完全包含（exact），不中再判最长公共子串占比：引用 ≥ 400 字时阈值 60%，短引用（≤12 字）要求 80%，避免短词误命中。

## 3. 能力契约
- 能力名 `source_check`，category `web`，实现 `packages/server/src/capabilities/capabilities/source-check.ts`。
- 入参：
  - `claims`: `[{url, quote}]`（推荐）：逐条给网址 + 你准备写进正文的原句/关键数字；
  - `urls`: 只有网址时传数组（1–8 个），只验证可访问性；
  - `text`: 直接传草稿正文，自动抽出里面的 http(s) 链接（去重、去尾标点、最多 8 个）；
  - `quote`: 配合 `urls`/`text` 用，同一句原句要核对多个链接时只写一次；
  - `maxChars`: 每个页面读取上限，默认 8000，范围 500–20000；
  - `strict`: true 时只要有一条未通过就让本次调用失败并列出问题。
- 返回：`{total, verified, reachableOnly, quoteNotFound, unreachable, summary, items[]}`；
  `items[i] = {url, ok, verdict, title, chars, quote, matchMode, matchRatio, snippet, message}`。
- 中文报错：没给来源「请提供要核对的来源…」、超过 8 条「一次最多核对 8 个链接，收到 N 个，请分批」、非 http「来源核对只接受 http(s) 网址：…」。

## 4. 提示词注入（`packages/worker/tool-loop.mjs`）
- `CAPABILITIES` 加 `source_check`；「可用工具」列表同步。
- `INSTRUCTIONS` 新增规则：引用外部数据、数字、结论或「某某报告显示」之后，交付前必须用 `source_check` 逐个核对，只有 `verified` 才能写成确定数据；`quote-not-found` / `unreachable` 必须改成「未核实」并说明原因或换来源。
- 桌面端执行器与本机打包都引用同一个 `tool-loop.mjs`，所以这条规则对云端 worker 与桌面执行器同时生效。

## 5. 验证
### 本地冒烟 `scripts/smoke-p48-source-check.mjs`（29 项，已接入 verify.ps1）
- 能力注册（descriptor / capability.service 挂载）；链接抽取（去重、去尾标点、上限 8、非 http 不抽）；归一化（全角、标点、大小写）；
- `quoteMatches` 的 exact / partial / missing / empty；入口校验中文 400；内网地址不判 verified 且提示「禁止访问内网」；工具循环接线断言。
- 不联网：真实联网核对放在生产验收，因为本地 SSRF 守卫禁止打 127.0.0.1。
### 生产验收 `scripts/prod-verify-p48.mjs`（15 项，生产实测 2026-11-13）
| 场景 | 期望 | 实测 |
| --- | --- | --- |
| `https://example.com` + 原句 `Example Domain` | verified | verified（mode=exact，chars=171，title=Example Domain） |
| 同页面 + 编造的长句 | quote-not-found | quote-not-found（mode=missing） |
| 不存在的域名 | unreachable | unreachable |
| `http://127.0.0.1:3000`（内网） | 不判 verified | unreachable +「打不开该链接：禁止访问内网或保留地址」 |
| `text` 入参 + `quote` | 自动抽链接并判 verified | 1 条，verified |
| 9 条链接 | 中文拒绝 | 「一次最多核对 8 个链接，收到 9 个，请分批」 |
| `ftp://` | 中文拒绝 | 「来源核对只接受 http(s) 网址」 |
| `strict:true` + 未通过 | 调用失败并列出问题 | 失败并列出未通过链接 |

### 真实业务验收（生产，`_deploy/p48-real-e2e.mjs`）
- 员工 boss-industry-researcher，要求「所有百分比/报告名称先 source_check 核对，没通过写未核实」。
- 结果：331 秒完成为 `awaiting_approval`，14 步：file_list / doc_read / web_search×3 / web_batch / **source_check×5** / invalid（模型输出抖动，已容错）/ doc_write / finish。
- 产出：`家装获客简报-可信版.docx`（10,368B，正文 1,673 字），末尾单列「来源清单」只列 2 条 verified 链接，并写明「未通过 source_check 抓取的第三方页面中的数字未在正文中引用」。
- 正文里出现 1 处「未核实」。积分 131 → 117（14 次模型请求）。
- 第一次尝试失败：93 秒后 `Bad Gateway Exception`，日志是 `upstream fetch failed` ×3（上游网络抖动）。为此增强了诊断：`providers.service.ts` 新增 `describeFetchError()`，把 `fetch failed` 的 `cause.code`（ECONNRESET/ETIMEDOUT/ENOTFOUND 等）写进日志和用户提示，下次抖动可直接定位。

## 6. 运维注意
- 核对内网/保留地址一律拒绝（复用 `web-extract` 的 SSRF 守卫），不能当内网探测通道用。
- 单次最多 8 个链接、每页面最多读 20000 字；多条链接串行，实测 example.com 约 1–4 秒/条，慢站点会拉长工具耗时（生产实测 5 次核对共 108 秒）。
- 该能力本身不计积分（能力调用不计费）；员工的模型请求照常计费。
- 0.1.31 客户端已打包本批改动（`tool-loop.mjs` 进 asar）；服务端 dist 已同步生产。
