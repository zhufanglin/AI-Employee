# P44 WP2 监控告警（fcmediaagent）

> 子 Agent B 产出。执行依据：docs/handoff/P44-运维保障-执行prompt.md 的 WP2；对应自检清单 A3「无监控告警」。
> 目标：六项检查每 5 分钟跑一次，异常落 `/opt/fcmediaagent/logs/monitor.log`（一行一个 JSON），并在配置了 `ALERT_WEBHOOK_URL` 时推送企业微信/钉钉机器人；同一项 60 分钟冷却内只推一次，恢复正常时推一次「已恢复」。

## 一、产物清单

| 文件（仓库内） | 部署到生产 | 作用 |
| --- | --- | --- |
| `scripts/ops/monitor.mjs` | `/opt/fcmediaagent/ops/monitor.mjs` | 监控主程序，Node 24 纯内置、零第三方依赖 |
| `scripts/ops/monitor.config.example.json` | 复制为 `/opt/fcmediaagent/ops/monitor.config.json`（可选） | 阈值示例文件，每个字段都有说明；不装则用内置默认值 |
| `ops/systemd/fcmediaagent-monitor.service` | `/etc/systemd/system/` | `Type=oneshot`，跑一次 `--once` |
| `ops/systemd/fcmediaagent-monitor.timer` | `/etc/systemd/system/` | `OnBootSec=2min` + `OnUnitActiveSec=5min` |
| `docs/handoff/P44-监控告警.md` | — | 本文档 |

## 二、六项检查

| # | check | 判定 | 默认阈值（配置项） |
| --- | --- | --- | --- |
| 1 | `api_health` | `GET http://127.0.0.1:3000/api/health`，HTTP 非 200，或响应体 `db != "up"`，或 3 秒超时 | 3 秒（`apiHealth.timeoutMs`） |
| 2 | `queue_backlog` | `EmployeeTask` 中 `status='queued'` 且 `createdAt` 早于 N 分钟前的条数 > 阈值 | 30 分钟 / 20 条（`queueBacklog.staleMinutes/threshold`） |
| 3 | `worker_heartbeat` | 两档判定（worker 只在有任务时写日志）：① `systemctl is-active fcmediaagent-worker` 为 `inactive`/`failed` → 立即告警；② 日志 mtime 超过 6 小时 → 告警（疑似卡死）；45–360 分钟无日志视为「进程存活、空闲」记 ok 并在 message 说明；文件不存在也告警 | 45 分钟新鲜 / 360 分钟告警（`workerHeartbeat.maxIdleMinutes/maxIdleAlertMinutes`），服务名 `serviceName` |
| 4 | `upstream_overdue` | 最近 200 行日志命中 `AccountOverdueError`（正则，大小写不敏感），命中行样本进告警详情 | 200 行（`upstreamOverdue.tailLines/pattern`） |
| 5 | `resources` | 磁盘 `/` 使用率 > 85%，或可用内存 < 300MB（合并为一项告警） | 85% / 300MB（`resources.*`） |
| 6 | `backup_freshness` | `/opt/fcmediaagent/backups/mysql` 下最新 `*.sql.gz` 的 mtime 超过 26 小时（目录缺失或没有备份也告警） | 26 小时（`backupFreshness.maxAgeHours`） |

队列检查不把密码放进 argv：从 `/opt/fcmediaagent/app/.env` 的 `DATABASE_URL` 解析出用户/密码/库名，再用 `docker exec -e MYSQL_PWD fcm-mysql mysql ...`，密码通过环境变量继承进容器，主机 `ps` 看不到，日志里若出现也会打码成 `***`。

## 三、生产安装（逐条执行）

在仓库根目录把 5 个文件传到生产（scp 到 /tmp 再 sudo 落位）：

```bash
# 1) 目录
sudo mkdir -p /opt/fcmediaagent/ops /opt/fcmediaagent/logs

# 2) 主程序 + 示例配置
sudo install -m 0755 -o root -g root /tmp/monitor.mjs /opt/fcmediaagent/ops/monitor.mjs
sudo install -m 0644 /tmp/monitor.config.example.json /opt/fcmediaagent/ops/monitor.config.example.json
# 需要改阈值时才装配置（不装即用内置默认值）
# sudo install -m 0644 /tmp/monitor.config.example.json /opt/fcmediaagent/ops/monitor.config.json

# 3) systemd 单元
sudo install -m 0644 /tmp/fcmediaagent-monitor.service /etc/systemd/system/fcmediaagent-monitor.service
sudo install -m 0644 /tmp/fcmediaagent-monitor.timer   /etc/systemd/system/fcmediaagent-monitor.timer

# 4) 可选：告警机器人地址（不要把 URL 写进仓库或 app/.env）
sudo install -m 0600 /dev/null /etc/default/fcmediaagent-monitor
sudo tee /etc/default/fcmediaagent-monitor >/dev/null <<'EOF'
ALERT_WEBHOOK_URL=https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxx
EOF

# 5) 先手工跑一次，确认六项输出
sudo -u root /opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --once; echo "exit=$?"
tail -n 10 /opt/fcmediaagent/logs/monitor.log

# 6) 启用定时器
sudo systemctl daemon-reload
sudo systemctl enable --now fcmediaagent-monitor.timer
systemctl list-timers fcmediaagent-monitor.timer --no-pager
sudo systemctl status fcmediaagent-monitor.timer --no-pager

# 7) 观察一轮触发（5 分钟后）
sudo journalctl -u fcmediaagent-monitor.service -n 30 --no-pager
```

说明：

- 定时器只负责按时拉起 service，单元文件里写的是 Node 绝对路径 `/opt/node/bin/node`（非交互环境没有 PATH）。
- `EnvironmentFile=-` 前面的短横线表示文件不存在也照常启动；该文件专放 `ALERT_WEBHOOK_URL`，不读 `app/.env`（避免 systemd 解析 .env 引号出问题）。
- `Type=oneshot` 下 `OnUnitActiveSec=5min` 从「上一次跑完」开始计时，不会因为某轮超时堆叠。
- 若生产 docker 不在默认 PATH，请在 `monitor.config.json` 里把 `queueBacklog.dockerBin` 设成绝对路径（如 `/usr/bin/docker`）。

## 四、命令行与退出码

```bash
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --once                    # 单跑一次（默认，写日志/写 state/推送）
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --dry-run               # 只打印，不写日志、不写 state、不推送
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --config /path/c.json    # 指定配置
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --strict                # 有告警时退出码 1（手工巡检用）
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --help
```

| 退出码 | 含义 |
| --- | --- |
| 0 | 本轮跑完（业务异常只记告警，不算脚本失败） |
| 1 | 写 `monitor.log` 失败，或 `--strict` 下存在告警 |
| 2 | 参数错误或配置文件不是合法 JSON |

`--dry-run` 在开发机（非 Linux、没有 `/opt`）会打印「未检测到生产环境……需要生产环境」并把不可用检查标为 `skipped`，退出码 0，不写任何文件、不推送。

## 五、配置项（`monitor.config.json`，全部可省略）

配置查找顺序：`--config` → 环境变量 `MONITOR_CONFIG` → 脚本同目录 `monitor.config.json` → `/opt/fcmediaagent/monitor.config.json` → `/opt/fcmediaagent/ops/monitor.config.json`。
以 `_` 开头的键是说明文字，会被忽略；未知键会在 stderr 打一行「配置警告」，不影响运行。

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `timeZone` | `Asia/Shanghai` | 推送消息里的时间展示时区 |
| `apiHealth.enabled` / `.url` / `.timeoutMs` | `true` / `http://127.0.0.1:3000/api/health` / `3000` | 健康检查 |
| `queueBacklog.enabled` / `.staleMinutes` / `.threshold` | `true` / `30` / `20` | 队列积压 |
| `queueBacklog.mysqlContainer` / `.dockerBin` / `.envFile` / `.timeoutMs` | `fcm-mysql` / `docker` / `/opt/fcmediaagent/app/.env` / `20000` | 取密码与执行环境 |
| `workerHeartbeat.enabled` / `.logPath` / `.maxIdleMinutes` / `.maxIdleAlertMinutes` / `.serviceName` | `true` / `/opt/fcmediaagent/logs/worker.log` / `45` / `360` / `fcmediaagent-worker` | worker 心跳（worker 每 30 分钟打 idle 日志，systemd 状态兜底） |
| `upstreamOverdue.enabled` / `.logPaths` / `.tailLines` / `.pattern` | `true` / `[worker.log, api.log]` / `200` / `AccountOverdueError` | 上游欠费 |
| `resources.enabled` / `.diskPath` / `.diskMaxUsedPercent` / `.memMinAvailableMB` | `true` / `/` / `85` / `300` | 磁盘与内存 |
| `backupFreshness.enabled` / `.backupDir` / `.maxAgeHours` | `true` / `/opt/fcmediaagent/backups/mysql` / `26` | 备份新鲜度 |
| `alert.webhookUrl` | 空 | 机器人 URL；空则依次读环境变量 `ALERT_WEBHOOK_URL`、`app/.env` 里的同名键 |
| `alert.cooldownMinutes` | `60` | 同一 check 的冷却分钟数 |
| `alert.stateFile` | `/opt/fcmediaagent/monitor-state.json` | 去重状态 |
| `alert.logFile` | `/opt/fcmediaagent/logs/monitor.log` | 监控日志 |
| `alert.webhookTimeoutMs` | `5000` | 推送超时，超时只记日志不影响退出码 |

调阈值举例（队列 30 条、worker 15 分钟、磁盘 90%）：

```json
{
  "queueBacklog": { "threshold": 30 },
  "workerHeartbeat": { "maxIdleMinutes": 15 },
  "resources": { "diskMaxUsedPercent": 90 }
}
```

（部分配置会与内置默认值深合并，只写要改的字段即可。）

## 六、日志格式与告警语义

`/opt/fcmediaagent/logs/monitor.log` 每行一个 JSON，字段固定为 `ts / check / level / message / detail`：

```json
{"ts":"2026-11-12T06:21:11.818Z","check":"worker_heartbeat","level":"alert","message":"worker 日志 40 分钟未更新（阈值 10 分钟）","detail":{"logPath":"/opt/fcmediaagent/logs/worker.log","idleMinutes":40,"maxIdleMinutes":10,"mtime":"…","sizeBytes":12345,"durationMs":4}}
```

- `level`：`ok`（正常）/ `alert`（异常）/ `skipped`（配置禁用或本机无生产环境）。
- 每轮 6 条检查行 + 1 条 `check:"run"` 汇总行；实际推送时再追加 1 条 `check:"push"`（含推送成功/失败）。
- 冷却内的告警仍每轮写 `alert` 行，但 `detail.suppressed=true` 并给出 `detail.cooldownUntil`，方便区分「持续异常」与「已推送」。
- `monitor-state.json` 结构：`{ "version":1, "updatedAt":…, "checks": { "<check>": { "alerting":true, "since":…, "lastAlertAt":…, "lastResult":"alert", "lastMessage":…, "lastOkAt":…, "recoveredAt":… } } }`；写入用 `.tmp-<pid>` + rename 原子替换，文件损坏时自动改名 `.broken-<ts>` 并重建。

推送行为：

- 一轮内多项异常合并成 **1 条** markdown 消息（`### 🔴 监控告警（N 项）`，逐项列标题 + 关键字段），恢复则发 `### ✅ 监控恢复（N 项）`。
- 机器人类型按 URL 自动识别：`dingtalk` → `{"msgtype":"markdown","markdown":{"title","text"}}`；`feishu/larksuite` → 纯文本；其他按企业微信 `{"msgtype":"markdown","markdown":{"content"}}`。返回体里的 `errcode` 非 0 视为推送失败。
- 钉钉机器人若用「自定义关键词」安全设置，关键词请填「监控」（消息标题含「监控告警/监控恢复」）。
- 日志里只记录打码后的地址（`https://host/***`），不会泄露 webhook token。

## 七、自检与排障

```bash
# 语法与依赖检查（在仓库根或生产上均可）
node --check /opt/fcmediaagent/ops/monitor.mjs

# 只看结果不产生副作用
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --dry-run

# 单跑并看最近一轮
/opt/node/bin/node /opt/fcmediaagent/ops/monitor.mjs --once && tail -n 7 /opt/fcmediaagent/logs/monitor.log

# 看最近告警条数
grep -c '"level":"alert"' /opt/fcmediaagent/logs/monitor.log

# 单独验证队列 SQL（不经过脚本）
docker exec -e MYSQL_PWD fcm-mysql mysql -u<user> -N -B -D fcmediaagent \
  -e "select count(*) from EmployeeTask where status='queued' and createdAt < (now() - interval 30 minute)"
```

| 现象 | 排查 |
| --- | --- |
| `queue_backlog` 报「未能解析 DATABASE_URL」 | 确认 `/opt/fcmediaagent/app/.env` 有 `DATABASE_URL`，且形如 `mysql://user:pass@127.0.0.1:3306/fcmediaagent` |
| `queue_backlog` 报 mysql 连接/权限错误 | 手工执行上面的 SQL；注意 `-e MYSQL_PWD` 必须跟在 `docker exec` 后、容器名前 |
| `api_health` 报请求失败 | `systemctl status fcmediaagent-api`；`curl -s http://127.0.0.1:3000/api/health` |
| 一直 `upstream_overdue` 告警 | 说明上游账户仍欠费：先充值/换渠道；恢复后新日志会滚出 200 行窗口，下一轮自然转 `ok` 并发「已恢复」；急用可重启 worker 让日志立刻翻新 |
| `backup_freshness` 告警 | `systemctl status fcmediaagent-backup.timer`；`ls -lt /opt/fcmediaagent/backups/mysql | head` |
| 推送失败 `errcode=...` | 企业微信查 key 是否失效、IP 白名单；钉钉查关键词/加签设置 |
| timer 不触发 | `systemctl list-timers fcmediaagent-monitor.timer`；`systemctl status fcmediaagent-monitor.service` |

## 八、与备份 / 日志轮转的衔接

- 备份由 WP1 的 `fcmediaagent-backup.timer` 每天生成 `/opt/fcmediaagent/backups/mysql/fcmediaagent-<YYYYmmdd-HHMMSS>.sql.gz`，本监控只看「最新文件 mtime 是否超过 26 小时」。备份策略改成每 12 小时一次时，这里可同步调小 `backupFreshness.maxAgeHours`。
- 日志轮转由 WP3 的 `logrotate` 负责：`copytruncate` 会保留文件句柄，`worker.log` 的 mtime 在轮转后仍会随新写入更新，因此不影响心跳判断；若轮转前 worker 已停写，心跳检查会先告警，属预期。
- `monitor.log` 同样在 `/opt/fcmediaagent/logs/*.log` 覆盖范围内，会被一起轮转压缩，不需要额外配置。

## 九、安全注意

- 不在仓库、文档、脚本里写任何密码或 webhook URL；密码只从 `app/.env` 解析并经环境变量传给容器，webhook 放 `/etc/default/fcmediaagent-monitor`（0600）。
- 脚本只读生产数据（一次 `count(*)`、读日志尾部、读 mtime），不做任何写库/改配置动作。
- 告警正文只带计数、路径、时间等运维信息；日志样本行截断到 240 字符。

## 十、回滚

```bash
sudo systemctl disable --now fcmediaagent-monitor.timer
sudo systemctl stop fcmediaagent-monitor.service
sudo rm -f /etc/systemd/system/fcmediaagent-monitor.timer /etc/systemd/system/fcmediaagent-monitor.service
sudo systemctl daemon-reload
# 可选：保留 /opt/fcmediaagent/ops/monitor.mjs 与 monitor.log 以备查
```

## 十一、未验证点（本机无生产环境，按纪律只做本机自检）

1. 未连生产 MySQL：`queue_backlog` 的 `docker exec -e MYSQL_PWD` 链路只在语法/参数层面验证过（本机触发了 docker 但容器不存在），需在生产手工跑一次确认返回条数。
2. 未真推企业微信/钉钉：本机用自建 HTTP 服务验证了 payload 结构与冷却/恢复逻辑，`errcode` 解析按官方文档实现，真实机器人需 lead 在生产配 URL 后观察一条。
3. systemd 单元未在 systemd 环境加载过（本机 Windows），已人工核对字段；`systemd-analyze verify` 需在生产执行。
4. 生产 `.env` 的 `DATABASE_URL` 若使用特殊字符（`@`/`:` 已在解析时 decode），需在生产确认用户名/库名解析正确。
5. 本机自检记录：`node --check` 通过；`--dry-run` 在 Windows 退出码 0 并打印「需要生产环境」；自建 webhook 下验证了「首次告警 → 冷却内不重推 → 恢复推一次 → 稳定不推」与 `--strict`/`--help`/坏配置的退出码。
