## T-31 桌面端：文生图 / 图生视频两个创作 tab

### 目标
客户端内直接出图、出片，不写代码也能用（当前 `MediaStudio.tsx` 只有「数字人对口型」和「音色克隆」）。

### 现有可复用的服务端接口（**已实测生产可用，不要重写**）
- `POST /api/media/images/generations` body `{ prompt: string, size?: number(默认7) }` → `{ taskId, status, estimatedAmount, upstream }`
- `POST /api/media/video/generations` body `{ image: string, prompt?: string, seconds?: number, aspectRatio?: '9:16'|'16:9'|'1:1'|'4:3'|'3:4' 或数字, version?: 1|2 }` → 同上
- `POST /api/media/files/upload` body `{ fileName, mime, base64 }`（或 `data`/`dataUrl`，上限 60MB）→ `{ fileName: 'openapi/xxx.jpg', url, type, size }`；**视频首帧必须先用它上传，拿 fileName 传给 `image`**
- `GET /api/media/tasks/:taskId` → MediaTaskRecord：`status` 只会是 `QUEUED|RUNNING|SUCCESS|FAILED`；成功时 `resultUrl` 已是**本站归档地址**（OSS 或 `/uploads/media/...`），`resultMeta` 含 `usage.consumeCoins`、`archivedBytes`
- 计费：提交即按 `MediaPricing` 预扣（image_gen 20 积分/次、video_gen 20 积分/次），上游失败自动退款；媒体任务**不吃免费额度**

### 要做的
1. `packages/desktop/src/main/index.ts` 补 IPC：`media:image`、`media:video`、`media:upload`、`media:task`（若已有 `media:*`，按其命名风格补齐，并在 `packages/desktop/src/preload/index.ts` 的 `window.fcm.media` 上暴露）。
2. `packages/desktop/src/renderer/src/pages/MediaStudio.tsx` 增加两个 tab：
   - **文生图**：提示词输入框 + 尺寸档位选择（1–8，默认 7）→ 提交 → 显示「排队中/生成中（已等待 X 分钟）」→ 成功显示图片（`<img src={resultUrl}>`）+ 下载/复制链接按钮 + 本次消耗积分。
   - **图生视频**：上传首帧图（本地选文件 → 读 base64 → `media:upload`）→ 提示词（默认 `Time-lapse photography`）→ 时长（默认 5 秒）→ 比例（默认 9:16）→ 提交 → 同一套轮询 → `<video controls src={resultUrl}>`。
3. 轮询沿用现有 `MediaStudio` 的 8s 间隔、不设上限，状态列必须显示累计等待时间（已有 `elapsed()` 可复用）。
4. 失败态要给出原因（扣费已退），不要只显示 FAILED。

### 实测耗时（据此写提示文案，别让用户以为卡死）
| 类型 | 出片耗时 | 上游成本 |
| --- | --- | --- |
| 文生图（size 7） | ≈215 秒 | ≈157 RH 币 |
| 图生视频（5 秒 / 9:16） | ≈3.5 分钟 | ≈149 RH 币 |
| 对口型（3 秒） | ≈96 秒 | ≈69 RH 币 |
| 智能混剪（15 秒） | ≈12 分钟（704 秒） | 按上游计 |

### 验收
- `electron-vite build` 通过；打包后 GUI 冒烟出一张图（用 `FCM_SMOKE_OUT` 截图留证）。
- 截图里能看到新 tab、提交后状态文案、成功后图片/视频。

## T-32 员工执行链路接入能力层与媒体生成（多步任务）

### 现状（问题）
- 桌面 `packages/desktop/src/main/executor.ts`：拿到任务 → **单轮** system+user 提示 → 调 `/compute/chat/completions` → 文本写文件 → PATCH `awaiting_approval`。
- 云端 `packages/worker/cloud-executor.mjs`：同样单轮文本。
- 结果：17 个 AI 员工只能「聊」，不能「查数据 / 出稿 / 出图 / 出片」，这是从「能聊」到「真干活」的最大空洞。

### 已就绪的积木
- 能力层：`GET /api/capabilities`、`POST /api/capabilities/run { name, params }` → `{ success, data, error, error_code }`；当前 7 个能力：`web_extract` / `content_save` / `content_query` / `distribution_save` / `customer_save` / `customer_query` / `llm_text`。
- 媒体：见 T-31 的接口（出图、出片）。
- 员工任务模型：`EmployeeTask`（含 `input`、`outputText`、`outputPath`、`outputMeta`、`artifacts`）、`EmployeeTaskArtifact`（`kind: text|file|image|video`、`path`、`mime`）。
- 服务端已有失联兜底：`recoverStalledTasks()`（`EMPLOYEE_TASK_STALL_MINUTES`，默认 5–10 分钟，二次超时置 failed）。

### 要做的
1. 给执行器加**工具循环**（最多 4 步，可 env 配置 `FCM_EXECUTOR_MAX_STEPS`）：
   - 模型可输出一个受控 JSON 指令，例如 `{"tool":"web_extract","params":{...}}` / `{"tool":"image_gen","params":{...}}` / `{"tool":"video_gen","params":{...}}` / `{"tool":"content_save","params":{...}}` / `{"tool":"finish","params":{"text":"..."}}`。
   - 执行器按指令调能力层或媒体接口，把结果摘要回灌给模型，直到 `finish` 或步数用尽。
   - **白名单**：只能在上述可用工具集合里选；未知工具直接拒绝并让模型重选。
2. 产物落库：文本 → `artifacts[kind=text]`；图片/视频 → 成功后 `artifacts[kind=image|video, path=resultUrl]` 并写 `outputMeta.media=[{taskId, url, credits}]`。
3. 超时/失败语义：工具失败不整体失败，回灌错误让模型继续；整任务超过 `FCM_EXECUTOR_TASK_TIMEOUT_MS`（默认 900000）才标 failed 并退款（媒体失败的退款由媒体层自己做）。
4. 同一套逻辑要能在 `packages/worker/cloud-executor.mjs` 复用（可抽成共享 `packages/worker/tool-loop.mjs`，桌面端用 ESM 动态 import 或复制；不要为了复用把桌面端改成 CJS）。

### 验收
- 冒烟脚本 `scripts/smoke-t32.mjs`：造一个员工任务（用 `boss-lead-radar`），断言任务跑完后 `artifacts` 至少 2 条、`outputMeta.steps` 记录每步工具与耗时；并入 verify。
- 真跑一次「出播报稿 + 配一张图」的任务，贴 outputText 与 image artifact 的 url。

## T-33 成本护栏：账号级限额 + 成本核算

### 现状（风险）
- 媒体提交即 `consumeCreditsWithPartial()` 预扣，上游失败退款；但**没有日/月上限**，一个脚本就能把余额烧光。
- 一次视频上游成本 ≈149–157 RH 币，而当前积分计价是占位价（用户说定价后面再说）→ 现在真放量等于**亏钱换数据**。
- `resultMeta.usage.consumeCoins` 已落库，但没有汇总口径与展示。

### 要做的
1. 账号级限额（env 可配，默认值取保守值）：
   - `MEDIA_DAILY_LIMIT`（默认 50 次/天/账号，按 `MediaTaskRecord.createdAt`）
   - `MEDIA_DAILY_SECONDS_LIMIT`（默认 600 秒/天/账号，按 `inputSeconds` 汇总）
   - `MEDIA_CONCURRENT_LIMIT`（默认 3，统计该用户 `status IN ('QUEUED','RUNNING')`）
   - 超限在**扣费前**拒绝，中文原因，例如「今日媒体生成次数已达上限（50 次），请明天再试或联系客服提升额度」。
2. 成本核算：
   - 新增聚合接口 `GET /api/media/usage/summary?days=7`（本人）与 `GET /api/admin/media/usage?days=30`（管理端）：按 taskType 汇总 次数 / 上游 consumeCoins / 我们收的积分 / 差额。
   - 若 `resultMeta.usage.consumeCoins` 存在且换算后**成本 > 收入**，把记录标 `resultMeta.costWarning = true`，管理端可筛。
3. 与现有余额封顶口径一致：余额不足时不要 402 到「扣一半」，媒体是**要么全退要么全扣**（现在已如此，别改坏）。

### 验收
- `scripts/smoke-t33.mjs`：造到限额边界，断言第 N+1 次在扣费前被拒（余额不变）；汇总接口数字与实际记录一致；并入 verify。
- 管理端 8 视图里「模型与媒体定价」页补一块「近 7 天媒体消耗」（可读汇总接口即可，不要求图表）。
