# P44 生产运维手册（fcmediaagent）

> 适用对象：接手 fcmediaagent 生产环境的同事。
> 生产机：`47.85.46.165`（阿里云弗吉尼亚，4C8G，Ubuntu 24.04.5）。**staging 154.64.255.36 只读，任何操作都不要碰。**
> 配套文档：`docs/handoff/P44-备份与恢复.md`（备份脚本细节）、`docs/handoff/P44-监控告警.md`（monitor 实现细节）、`docs/handoff/部署-47.85.46.165.md`（首次部署记录）、`docs/handoff/更新服务器.md`（桌面更新源）。
> 本手册中的命令均按上述生产事实编写；执行前先确认当前所在机器（本地 Windows 还是生产机）。

## 0. 先读这一页：事故优先级

| 级别 | 场景 | 第一动作 |
| --- | --- | --- |
| P0 | 全站不可用（健康检查失败、nginx 502、MySQL 挂） | 先恢复服务，再查原因：§5.1、§5.5、§6.1、§6.6 |
| P0 | 磁盘满 / 内存耗尽导致服务反复重启 | 先腾空间/重启，避免数据库损坏：§5.5、§6.4 |
| P1 | 上游欠费 403，对话/员工任务全失败 | 确认欠费并充值，无需改代码：§5.4、§6.2 |
| P1 | worker 不心跳、任务积压 | 先重启 worker 恢复队列：§5.2、§5.3、§6.5 |
| P1 | SSH 连不上 | 不要狂试；按重试策略 + 阿里云 VNC：§6.3 |
| P2 | 备份超过 26 小时未成功 | 手工补一次并查明 timer/磁盘：§5.6 |
| P2 | 日志不轮转、磁盘缓慢增长 | 检查 `/etc/logrotate.d/fcmediaagent`：§5.5 |

三条铁律：

1. **先备份再破坏性操作**。覆盖数据库、删数据、改 SSH 之前，必须有一份可校验的备份（§4）。
2. **改配置先干跑**。`logrotate -d`、`backup-prod.sh --dry-run`、`monitor.mjs --dry-run`、`nginx -t`、`sshd -t`。
3. **保留退路**。改 SSH 至少留一个已登录会话 + 阿里云控制台 VNC；发布前保留上一版 dist/asar。

## 2. 日常发布流程

### 2.0 发布前检查（每次都要做）

1. 确认有人值守，避开任务高峰；在群里说明发布窗口。
2. 做一次数据库备份并校验（§4.2），记录文件名。
3. 生产资源正常：`df -h /` 使用率 < 85%，`free -m` 可用 > 300MB，`systemctl is-active fcmediaagent-api fcmediaagent-worker` 均 active。
4. 本地构建通过，变更范围明确；**改了 `prisma/schema.prisma` 或 migrations 的发布要单独评估**（§2.2）。

### 2.1 服务端 dist + worker 发布

#### 第 1 步：本地构建

~~~powershell
cd C:/Users/30290/Desktop/fcmediaagent-replica
npm -w packages/server run build
Test-Path packages/server/dist/main.js
~~~

必须输出 `True`。若构建失败，停止发布。

#### 第 2 步：本地打包（dist + 两个 worker 文件）

~~~powershell
cd C:/Users/30290/Desktop/fcmediaagent-replica
$TS = Get-Date -Format 'yyyyMMdd-HHmmss'
$stage = "_deploy/stage-$TS"
New-Item -ItemType Directory -Force "$stage/worker" | Out-Null
Copy-Item -Recurse packages/server/dist "$stage/dist"
Copy-Item packages/worker/tool-loop.mjs, packages/worker/cloud-executor.mjs "$stage/worker/"
tar -czf "_deploy/deploy-$TS.tgz" -C $stage .
Write-Host "打包完成：_deploy/deploy-$TS.tgz，时间戳 $TS"
~~~

记下输出的 `$TS`，后面远端要用同一个值。

#### 第 3 步：上传

~~~powershell
$TS = "把上一步的时间戳贴这里"
scp -i ~/.ssh/fcmediaagent_deploy "_deploy/deploy-$TS.tgz" root@47.85.46.165:/opt/fcmediaagent/
~~~

ssh/scp 偶发 `Connection refused`：等 5–10 秒重试，最多 8 次（§6.3），不要连续狂点。

#### 第 4 步：远端解包、备份旧版、切换、重启

~~~bash
TS=20261112-153000   # 换成第 2 步的真实时间戳
cd /opt/fcmediaagent

# 4.1 解包并校验关键文件存在
rm -rf "deploy-$TS" && mkdir -p "deploy-$TS"
tar -xzf "deploy-$TS.tgz" -C "deploy-$TS"
test -f "deploy-$TS/dist/main.js"
test -f "deploy-$TS/worker/tool-loop.mjs"
test -f "deploy-$TS/worker/cloud-executor.mjs"

# 4.2 备份当前版本（回滚靠它）
cp -a app/dist "app/dist.bak.$TS"
cp -a worker/tool-loop.mjs "worker/tool-loop.mjs.bak.$TS"
cp -a worker/cloud-executor.mjs "worker/cloud-executor.mjs.bak.$TS"

# 4.3 覆盖（先停服务；dist 整个删掉再拷，避免旧版本已删除的文件残留）
systemctl stop fcmediaagent-api fcmediaagent-worker
rm -rf app/dist
cp -a "deploy-$TS/dist" app/dist
cp "deploy-$TS/worker/tool-loop.mjs" "deploy-$TS/worker/cloud-executor.mjs" worker/

# 4.4 重启并验证
systemctl restart fcmediaagent-api fcmediaagent-worker
sleep 6
systemctl is-active fcmediaagent-api fcmediaagent-worker
curl -fsS http://127.0.0.1:3000/api/health; echo
~~~

`systemctl is-active` 两行都必须是 `active`，健康接口必须是 `{"status":"ok","db":"up"}`。任一不满足立刻回滚（§3.1）。

若第 4.3 步中途失败（`cp` 报错、文件没拷完）：先 `rm -rf app/dist && cp -a "app/dist.bak.$TS" app/dist` 还原旧版，再 `systemctl restart fcmediaagent-api fcmediaagent-worker`；不要带着半套 dist 启动。

#### 第 5 步：发布后验证

参考 §2.5。至少验证：后台能登录、发一条对话、员工任务能跑、桌面端能连上。

### 2.2 数据库迁移（仅当本次包含 prisma 变更）

> 只有 `packages/server/prisma/schema.prisma` 或 `prisma/migrations/` 有变化时才需要。
> 迁移是**前向不可逆**的：先备份（§4.2），并想清楚回滚代码时数据库是否还兼容。

~~~bash
cd /opt/fcmediaagent/app
cp -a .env ".env.bak.$(date +%Y%m%d-%H%M%S)"
PATH=/opt/node/bin:$PATH /opt/node/bin/npx prisma migrate deploy
~~~

然后重启 `fcmediaagent-api` 与 `fcmediaagent-worker`，再跑健康检查。
若迁移失败：**不要重复执行**，先看 `prisma/migrations` 与错误信息；需要恢复时走 §4.4。

### 2.3 桌面整包发布（Windows）

适用：Electron/依赖/extraResources 变化，或需要让老客户端强制升级。

~~~powershell
cd C:/Users/30290/Desktop/fcmediaagent-replica/packages/desktop

# 1) 先改 package.json 的 version（例如 0.1.26），必须与要发布的版本一致
# 2) 构建 + 打 NSIS 安装包（产物在 release/）
npm run dist

# 3) 确认产物：latest.yml + fcmediaagent-ai-employee-<version>-win-x64.exe
Get-ChildItem release | Select-Object Name, Length
~~~

回到仓库根发布：

~~~powershell
cd C:/Users/30290/Desktop/fcmediaagent-replica
node scripts/publish-update.mjs --dry-run   # 只打印将执行的命令
node scripts/publish-update.mjs             # 上传并自动校验 HTTP 状态
~~~

上传约 127MB，慢时 1–2 分钟，**不要中途 Ctrl+C**。脚本会校验 `latest.yml=200`、exe 支持 Range=206。

手工复核：

~~~bash
curl -fsS https://updates.fcmediaagent.com/desktop/latest/latest.yml
curl -fsSI https://updates.fcmediaagent.com/desktop/latest/fcmediaagent-ai-employee-0.1.26-win-x64.exe | head -1
~~~

注意：

- 产物名必须是 ASCII，不要手改 `latest.yml` 里的 `path`；版本号、exe 文件名、yml 三者必须一致。
- 发布前把上一版 exe 与 latest.yml 另存到本地 `_deploy/desktop-backup-<version>/`，回滚要用（§3.4）。
- 客户端默认从 `https://updates.fcmediaagent.com/desktop/latest` 检查更新。

### 2.4 asar 热更新（日常小改，最快）

适用：只改了 `packages/desktop/out/` 里的主进程/渲染代码，Electron 版本、原生依赖、`extraResources/`（skills/context/openclaw）**没变**。
不适用：改了依赖、Electron 版本、extraResources、安装器配置——这些必须走整包（§2.3）。

~~~powershell
cd C:/Users/30290/Desktop/fcmediaagent-replica

# 1) 先确认 packages/desktop/package.json 的 version 已递增，并已 npm run dist 产出 win-unpacked
Test-Path packages/desktop/release/win-unpacked/resources/app.asar

# 2) 本地只打包，不传输
node scripts/publish-asar.mjs --dry-run
node scripts/publish-asar.mjs

# 3) 上传前备份服务端清单（回滚用）
ssh -i ~/.ssh/fcmediaagent_deploy root@47.85.46.165 "cd /opt/fcmediaagent/updates/desktop/asar && cp -a asar.json asar.json.bak.$(date +%Y%m%d-%H%M%S) && ls -l"

# 4) 上传并校验
node scripts/publish-asar.mjs --upload
~~~

验证：

~~~bash
curl -fsS https://updates.fcmediaagent.com/desktop/asar/asar.json
~~~

应返回包含 `version`、`file`、`sha512`、`size` 的 JSON，且 `file` 是纯文件名（如 `fcmediaagent-ai-employee-0.1.26-asar.bin`）。
客户端操作：设置 → 检查更新 → 下载 → 安装（客户端会备份 `resources/app.asar` 为 `app.asar.bak-<时间戳>` 后替换并自动重启）。

注意：

- `publish-asar.mjs` 默认只打包，**必须加 `--upload` 才会传到生产**。
- `version` 必须与 `package.json` 一致；`--min-version` 用于阻止过老客户端直接吃新 asar（老客户端应先装整包）。
- 每次上传前备份 `asar.json`（第 3 步），否则无法把更新源指回旧版。

### 2.5 发布后验证清单

## 3. 回滚流程

### 3.1 服务端 dist 回滚

适用：新 dist 导致 API 起不来、健康检查失败、接口 500。

~~~bash
cd /opt/fcmediaagent

# 1) 找到最近一次备份（按时间倒序）
ls -d app/dist.bak.* | sort | tail -5

# 2) 停 API，保留故障现场，再把备份换回来
# 按文件名里的时间戳排序（cp -a 会保留 mtime，不能用 ls -t）
TS=$(ls -d app/dist.bak.* | sort | tail -1 | sed 's#app/dist.bak.##')
systemctl stop fcmediaagent-api
mv app/dist "app/dist.failed.$(date +%Y%m%d-%H%M%S)"
cp -a "app/dist.bak.$TS" app/dist

# 3) 启动并验证
systemctl start fcmediaagent-api
sleep 5
systemctl is-active fcmediaagent-api
curl -fsS http://127.0.0.1:3000/api/health; echo
~~~

若成功，再决定是否清理 `dist.failed.*`（确认无需留证后再删）。

### 3.2 worker 文件回滚

~~~bash
cd /opt/fcmediaagent
ls worker/tool-loop.mjs.bak.* | sort | tail -3
# 按文件名时间戳排序（cp -a 保留 mtime，不能用 ls -t）
TS=$(ls worker/tool-loop.mjs.bak.* | sort | tail -1 | sed 's#worker/tool-loop.mjs.bak.##')

systemctl stop fcmediaagent-worker
cp -a "worker/tool-loop.mjs.bak.$TS" worker/tool-loop.mjs
cp -a "worker/cloud-executor.mjs.bak.$TS" worker/cloud-executor.mjs
systemctl start fcmediaagent-worker
sleep 5
systemctl is-active fcmediaagent-worker
tail -n 50 /opt/fcmediaagent/logs/worker.log
~~~

注意：dist 与 worker 可能同批发布；回滚时两者要回到**同一时间戳**，不要只回滚一半。

### 3.3 asar 热更新回滚（客户端）

适用：新 asar 导致客户端白屏/崩溃/功能异常。

1. 完全退出客户端（任务栏右键退出，确认任务管理器里没有残留进程）。
2. 找到安装目录的 `resources`：

~~~powershell
# 默认在 %LOCALAPPDATA%/Programs/中科元晟 AI员工/resources
# 若安装时改过目录，用桌面快捷方式 → 右键 → 打开文件所在位置
$exe = (Get-Process | Where-Object { $_.MainWindowTitle -like '*中科元晟*' } | Select-Object -First 1).Path
if (-not $exe) { Write-Host '客户端未运行，请用快捷方式定位安装目录' }
$res = Join-Path (Split-Path $exe) 'resources'
Get-ChildItem $res -Filter 'app.asar.bak-*' | Sort-Object LastWriteTime -Descending | Select-Object -First 5 Name, LastWriteTime
~~~

3. 把最近的备份复制回 `app.asar`：

~~~powershell
$res = "把上面得到的 resources 路径贴这里"
$bak = Get-ChildItem $res -Filter 'app.asar.bak-*' | Sort-Object LastWriteTime -Descending | Select-Object -First 1
Copy-Item $bak.FullName (Join-Path $res 'app.asar') -Force
Write-Host "已回滚到 $($bak.Name)"
~~~

4. 重新启动客户端验证。

**重要**：只回滚单台客户端不够——更新源 `asar.json` 仍指向坏版本，其他客户端还会中招。必须同时处理服务端：

~~~bash
ssh -i ~/.ssh/fcmediaagent_deploy root@47.85.46.165 \
  'cd /opt/fcmediaagent/updates/desktop/asar && ls -1 asar.json.bak.* | sort | tail -5'
# 最新备份就是坏版本发布前的清单；若之后又发布过，先按时间挑对再执行
ssh -i ~/.ssh/fcmediaagent_deploy root@47.85.46.165 \
  'cd /opt/fcmediaagent/updates/desktop/asar && cp -a "$(ls -1 asar.json.bak.* | sort | tail -1)" asar.json && cat asar.json'
~~~

恢复后确认 `curl -fsS https://updates.fcmediaagent.com/desktop/asar/asar.json` 里的 `version` 是旧版本。坏版本的 `.bin` 可以留在目录里（不引用即可），不要删证据。

### 3.4 桌面整包回滚

适用：整包安装后大面积故障，asar 也救不了。

1. 用本地保留的上一版 `fcmediaagent-ai-employee-<旧版本>-win-x64.exe` 重新安装（安装器为 per-user，`deleteAppDataOnUninstall: false`，用户数据保留）。
2. 同时把更新源指回旧版：把上一版 `latest.yml` 与 exe 重新上传到 `/opt/fcmediaagent/updates/desktop/latest/`（覆盖当前 latest.yml），否则客户端会再次自动升级。
3. 让用户重启客户端确认版本号。

> 若上一版文件已丢失：从任一仍在使用旧版的机器 `resources` 里取不到 exe，只能回滚代码后重新打包一个**版本号更高**的修复版（推荐做法），不要硬改 `latest.yml` 的版本号。

### 3.5 数据库迁移的回滚原则

- 代码回滚 ≠ 数据库回滚。若新代码执行过 destructive migration（删列/改类型），旧代码可能直接报错。
- 优先**前向修复**（发一个兼容旧 schema 的补丁），其次才用备份恢复（§4.4）。
- 恢复生产库会丢失备份点之后的数据，必须业务确认后再做。

## 4. 备份与恢复

脚本与实现细节见 `docs/handoff/P44-备份与恢复.md`；本节是操作流程。

### 4.1 备份策略

| 项 | 值 |
| --- | --- |
| 内容 | 整库 `fcmediaagent`（mysqldump --single-transaction --quick --routines --events） |
| 频率 | 每日一次（`fcmediaagent-backup.timer`） |
| 本地保留 | 14 天，自动清理更早的 `.sql.gz` 与 `.sha256` |
| 完整性 | 每个备份生成 `.sha256`；导出后先 `gzip -t` |
| 异地 | 可选 `--oss` 上传到 OSS 桶 `zhongke001` 的 `backups/mysql/`；失败只告警，不影响本地备份 |
| 目录权限 | `/opt/fcmediaagent/backups` 700，仅 root |

### 4.2 手工备份（发布前/危险操作前必做）

~~~bash
# 先空跑，确认解析到的库、容器、输出路径正确（不会真的导出）
/opt/fcmediaagent/ops/backup-prod.sh --dry-run

# 真正执行（本地）
/opt/fcmediaagent/ops/backup-prod.sh

# 需要异地备份时
/opt/fcmediaagent/ops/backup-prod.sh --oss
~~~

校验（必须输出 `OK`）：

~~~bash
cd /opt/fcmediaagent/backups/mysql
ls -lht | head -5
sha256sum -c "$(ls -t *.sql.gz.sha256 | head -1)"
gzip -t "$(ls -t *.sql.gz | head -1)" && echo "gzip OK"
~~~

记录本次文件名（如 `fcmediaagent-20261112-031500.sql.gz`），后续回滚/恢复引用它。

### 4.3 恢复演练（建议每月一次）

**默认模式只导入临时库，不碰生产库**，可以随时做：

~~~bash
cd /opt/fcmediaagent
FILE=$(ls -t backups/mysql/*.sql.gz | head -1)
echo "演练文件：$FILE"
/opt/fcmediaagent/ops/restore-prod.sh "$FILE"
~~~

脚本会创建 `fcm_restore_<时间戳>` 临时库，导入后打印表数量（与生产表数量应基本一致），完成后按提示清理。
若脚本未自动清理，手工确认并删除临时库：

~~~bash
# 先按 §5.0 定义 mysqlq（用 app/.env 的账号，脚本建库/删库也是这个账号）
mysqlq "show databases like 'fcm_restore_%';"
# 确认名字后删除（把库名换成实际值）
mysqlq "drop database if exists fcm_restore_20261112_031500;"
~~~

演练验收：退出码 0、表数量合理（40+ 张）、无 `ERROR 1044/1045` 权限错误、宿主机剩余空间足够（备份解压后约为原库大小）。

### 4.4 生产恢复（覆盖生产库，高危）

> 只在确认数据损坏/误删且无法前向修复时执行。**先读 §3.5，确认业务接受丢失备份点之后的数据。**
> 执行前在群里通知，并确保当前没有正在跑的员工任务/发布。

~~~bash
# 1) 停写入
systemctl stop fcmediaagent-worker fcmediaagent-api

# 2) 选一个已验证的备份
cd /opt/fcmediaagent
ls -lht backups/mysql/*.sql.gz | head -5
FILE=$(ls -t backups/mysql/*.sql.gz | head -1)

# 3) 覆盖恢复（脚本会先做一次即时备份；必须按提示输入 YES）
/opt/fcmediaagent/ops/restore-prod.sh "$FILE" --apply

# 4) 启动并验证
systemctl start fcmediaagent-api fcmediaagent-worker
sleep 6
systemctl is-active fcmediaagent-api fcmediaagent-worker
curl -fsS http://127.0.0.1:3000/api/health; echo
~~~

恢复后抽查：后台登录、用户/订单数量、最近一条员工任务、对话记录。若健康检查报数据库错误，先看 `restore-prod.sh` 输出和 `api.log`，不要重复执行 `--apply`。

### 4.5 下载备份到本地 / 灾难场景

~~~powershell
scp -i ~/.ssh/fcmediaagent_deploy root@47.85.46.165:/opt/fcmediaagent/backups/mysql/fcmediaagent-20261112-031500.sql.gz .
~~~

整机丢失时：按 `docs/handoff/部署-47.85.46.165.md` 重建 ECS/环境 → 从 OSS 取最新备份 → 恢复 → 切 DNS。**备份在异地（OSS）才有意义，建议开启 `--oss`。**

## 5. 告警处置手册

监控每 5 分钟跑一次（`fcmediaagent-monitor.timer`），六项检查：

| check | 含义 | 默认阈值 |
| --- | --- | --- |
| `api_health` | API 健康接口 | 非 200 或 `db != up` |
| `queue_backlog` | 员工任务积压 | queued 且超过 30 分钟的任务 > 20 条 |
| `worker_heartbeat` | worker 心跳 | `worker.log` 超过 10 分钟未更新 |
| `upstream_overdue` | 上游欠费 | 最近 200 行日志出现 `AccountOverdueError` |
| `resources` | 磁盘/内存 | 磁盘 > 85% 或可用内存 < 300MB |
| `backup_freshness` | 备份新鲜度 | 最新 `.sql.gz` 超过 26 小时 |

### 5.0 告警怎么读 / 通用工具

~~~bash
# 最近告警（一行一个 JSON：ts/check/level/message/detail）
tail -n 50 /opt/fcmediaagent/logs/monitor.log
grep -E '"level": *"alert"' /opt/fcmediaagent/logs/monitor.log | tail -n 20

# 去重状态（哪个 check 正在告警）
cat /opt/fcmediaagent/monitor-state.json

# 看 timer/service 最近一次执行
systemctl status fcmediaagent-monitor.timer --no-pager
systemctl status fcmediaagent-monitor.service --no-pager -l | tail -20
~~~

同一 check 60 分钟内只推一次，恢复时会推一次「已恢复」。不要为了消警直接删 `monitor-state.json`（会导致重复推送）；只有确认告警已恢复、需要强制重推时才删。

**SQL 小工具**：在同一个 shell 里粘贴一次，后续 `mysqlq "SQL"` 直接查库（密码从 `.env` 读，不打印）：

~~~bash
mysqlq() {
  local sql="$1" db="$2" url user pass
  [ -n "$db" ] || db=fcmediaagent
  url=$(grep -E '^DATABASE_URL=' /opt/fcmediaagent/app/.env | tail -n 1 | cut -d= -f2-)
  user=$(printf '%s' "$url" | sed -E 's#^[^:]+://([^:]+):.*#\1#')
  pass=$(printf '%s' "$url" | sed -E 's#^[^:]+://[^:]+:([^@]*)@.*#\1#')
  docker exec -e MYSQL_PWD="$pass" fcm-mysql mysql -h127.0.0.1 -u"$user" -N -B -e "$sql" "$db"
}
~~~

若密码含 `%XX` 转义导致认证失败，改用 `backup-prod.sh --dry-run` 观察解析结果，或临时用容器内 `mysql` 客户端排查。

### 5.1 api_health：API 健康检查失败

**第一步**：本机直连 3000 端口，确认是 API 挂了还是 nginx/公网问题。

~~~bash
curl -v --max-time 5 http://127.0.0.1:3000/api/health
systemctl status fcmediaagent-api --no-pager -l | tail -30
ss -lntp | grep ':3000'
tail -n 100 /opt/fcmediaagent/logs/api.log
docker ps --filter name=fcm-mysql --format '{{.Names}} {{.Status}}'
df -h /; free -m
~~~

**止血**：

- 进程不在/反复重启：`systemctl restart fcmediaagent-api`，再看日志。
- 日志报 Prisma `P1001`：先按 §6.1 恢复 MySQL，再重启 API。
- 磁盘满/内存耗尽：按 §6.4 先腾空间，再重启。
- 只有公网 443 失败、本机 3000 正常：检查 nginx（§6.6），`nginx -t && systemctl reload nginx`。

**根治**：拿到日志里的第一处错误再改；不要用“重启大法”掩盖 crash loop。重启后观察 10 分钟，确认 `monitor.log` 恢复 ok。

### 5.2 queue_backlog：员工任务积压

**第一步**：确认 worker 是否活着、积压是什么状态、最老任务多久。

~~~bash
mysqlq "select status, count(*) as n from EmployeeTask group by status;"
mysqlq "select id, userId, employeeId, status, createdAt from EmployeeTask where status='queued' order by createdAt limit 20;"
mysqlq "select count(*) from EmployeeTask where status='queued' and createdAt < now() - interval 30 minute;"
systemctl status fcmediaagent-worker --no-pager -l | tail -30
tail -n 100 /opt/fcmediaagent/logs/worker.log
~~~

**止血**：

- worker 挂了/卡死：`systemctl restart fcmediaagent-worker`，观察日志是否恢复消费。
- 上游 403 欠费：任务会一直失败重试，先按 §5.4 充值，不要删任务。
- 单任务长期 `running`（worker 崩溃导致）：确认没有进程在执行后，才考虑把该任务改回 `queued`（需业务确认，SQL 改动前先备份）。
- 大量任务同时涌入：属于容量问题，评估错峰/扩容，不要直接清空队列。

**根治**：区分「worker 不工作」还是「上游不可用」；前者修进程/代码，后者修账号。恢复后确认 queued 数量持续下降。

### 5.3 worker_heartbeat：worker 不心跳

**第一步**：看日志文件是否真的停更，以及进程是否还活着。

~~~bash
stat -c '%y %n' /opt/fcmediaagent/logs/worker.log
date
systemctl status fcmediaagent-worker --no-pager -l | tail -30
ps -eo pid,etime,rss,cmd | grep -E 'tool-loop|cloud-executor' | grep -v grep
tail -n 100 /opt/fcmediaagent/logs/worker.log
free -m; df -h /
~~~

**止血**：

- 进程不存在或卡死：`systemctl restart fcmediaagent-worker`，等 1 分钟看 `worker.log` 是否更新。
- 日志报数据库连不上：按 §6.1 处理。
- 日志报上游 403：按 §5.4 处理。
- 内存不足/OOM：`dmesg -T | grep -i -E 'oom|killed process'` 确认后按 §6.4 处理。

**注意**：worker 空转时如果本来就不打日志，`mtime` 也会变旧。确认进程、数据库、队列都正常后，可把 `monitor.config.json` 的 `workerHeartbeat.maxIdleMinutes` 调大（改完下一次生效，无需重启 timer），不要长期忽略该告警。

### 5.4 upstream_overdue：上游欠费（AccountOverdueError）

**第一步**：确认日志里确实是欠费，而不是偶发 429/超时。

~~~bash
grep -n 'AccountOverdueError' /opt/fcmediaagent/logs/api.log /opt/fcmediaagent/logs/worker.log | tail -n 20
grep -c '^ARK_API_KEY=' /opt/fcmediaagent/app/.env    # 只确认 key 存在，不要打印值
tail -n 50 /opt/fcmediaagent/logs/monitor.log
~~~

特征错误：`403 {"error":{"code":"AccountOverdueError","message":"The request failed because your account has an overdue balance."}}`。
影响范围：对话、员工任务、记忆、`llm_text`；**媒体/OSS 相关功能不受影响**。

**止血**：到上游控制台充值/处理欠费。代码层面没有可修的；不要通过重启服务“掩盖”，也不要关闭告警。

**验证**：充值后等 5–10 分钟，发一条对话/跑一个最小员工任务，确认日志不再新增 `AccountOverdueError`；恢复后 monitor 会推「已恢复」。

### 5.5 resources：磁盘或内存告警

**第一步**：定位是磁盘还是内存，谁在占。

~~~bash
df -h /
du -xhd1 /opt /var /root 2>/dev/null | sort -h | tail -20
docker system df
free -m
ps -eo pid,rss,pmem,cmd --sort=-rss | head -15
dmesg -T | grep -i -E 'oom|killed process' | tail -20
~~~

**止血（磁盘）**：

~~~bash
# 1) 强制轮转日志（systemd append 句柄，必须 copytruncate）
logrotate -f /etc/logrotate.d/fcmediaagent
ls -lh /opt/fcmediaagent/logs/

# 2) 清理 14 天前旧备份（脚本日常会做；先确认保留最新一份）
find /opt/fcmediaagent/backups/mysql -maxdepth 1 -name '*.sql.gz' -mtime +14 -print
# 确认列表无误后再加 -delete

# 3) 清 docker 悬空镜像（不要加 --volumes，不要动 fcm-mysql）
docker image prune -f

# 4) 找已删除但仍被进程占用的文件（重启对应服务可释放）
lsof +L1 2>/dev/null | head -20
~~~

**止血（内存）**：`systemctl restart fcmediaagent-worker`（先 worker，影响小）；仍不足再 `systemctl restart fcmediaagent-api`。API 有 `--max-old-space-size=768`；若长期不足，评估升级配置/限制并发，不要靠反复重启。

**根治**：确认日志轮转生效（`logrotate -d` 无 error、`logrotate.timer` 在跑）、备份保留策略生效、没有异常大文件/容器日志。查看容器日志大小：`docker inspect --format '{{.LogPath}}' fcm-mysql` 后 `du -h` 对应文件。

### 5.6 backup_freshness：备份超过 26 小时未更新

**第一步**：确认 timer 是否在跑、最近一次失败原因。

~~~bash
systemctl status fcmediaagent-backup.timer --no-pager
systemctl status fcmediaagent-backup.service --no-pager -l | tail -30
journalctl -u fcmediaagent-backup.service -n 80 --no-pager
tail -n 50 /opt/fcmediaagent/logs/backup.log
ls -lht /opt/fcmediaagent/backups/mysql | head -5
df -h /opt/fcmediaagent/backups
docker ps --filter name=fcm-mysql --format '{{.Names}} {{.Status}}'
~~~

**止血**：修复原因（磁盘/容器/权限）后手工补一次：

~~~bash
/opt/fcmediaagent/ops/backup-prod.sh
cd /opt/fcmediaagent/backups/mysql && sha256sum -c "$(ls -t *.sql.gz.sha256 | head -1)"
~~~

**常见原因**：timer 被 disable、容器未启动、`app/.env` 不可读、备份盘满、`mysqldump` 权限被改。修完确认 `monitor.log` 的 `backup_freshness` 恢复 ok。

## 6. 常见故障

### 6.1 Prisma P1001：连不上数据库

**典型日志**：`PrismaClientInitializationError` / `P1001: Can't reach database server at 127.0.0.1:3306`。

~~~bash
docker ps -a --filter name=fcm-mysql
docker start fcm-mysql          # 仅在容器存在但停止时
docker logs --tail 100 fcm-mysql
docker port fcm-mysql
mysqlq "select 1;" || true
ss -lntp | grep ':3306'
df -h /                          # 磁盘满会导致 MySQL 起不来/崩溃
free -m
tail -n 100 /opt/fcmediaagent/logs/api.log
~~~

处理顺序：容器是否运行 → 容器日志是否报磁盘/InnoDB 错误 → 端口是否监听 → `.env` 的 `DATABASE_URL` 是否被误改（对比备份 `.env.bak.*`）。
确认 `DATABASE_URL` 指向 `127.0.0.1:3306/fcmediaagent` 且账号密码正确。
MySQL 恢复后重启 `fcmediaagent-api` 与 `fcmediaagent-worker`，再验证健康接口。
**不要**在数据库未恢复时反复重启 API，会产生大量错误日志并拖慢恢复。

### 6.2 上游 403 AccountOverdueError

见 §5.4。补充：

- 该错误是**账号欠费**，不是 key 失效/网络问题；换 key 无效。
- 媒体生成走其他通道，可能仍正常，容易误判“服务没挂”。
- 充值后用一条真实对话验证；若仍 403，检查是否多个上游账号/多个 key，确认 `.env` 里实际生效的是哪一个。

### 6.3 SSH 22 Connection refused / 连不上

先按纪律重试：**间隔 5–10 秒，最多 8 次**。仍失败则用阿里云控制台 **VNC/远程连接** 登录（不依赖 SSH），按顺序查：

~~~bash
systemctl status ssh --no-pager
ss -lntp | grep -E ':22|:2222'
sshd -t
journalctl -u ssh -n 100 --no-pager
df -h /; free -m
fail2ban-client status sshd 2>/dev/null || true
~~~

常见原因与处理：

| 原因 | 判断 | 处理 |
| --- | --- | --- |
| 安全组没放行你的 IP | 换手机热点/其他网络也不行 | 阿里云控制台 → 安全组，临时放行当前公网 IP 的 SSH 端口 |
| fail2ban 封了你的 IP | `fail2ban-client status sshd` 的 Banned IP list 有你 | 控制台执行 `fail2ban-client set sshd unbanip 203.0.113.10`（换成实际 IP）；并把办公 IP 加到 `ignoreip` |
| sshd 没起来/配置错 | `systemctl status ssh` 失败，`sshd -t` 报错 | 恢复最近的 `sshd_config.bak.*`，`sshd -t && systemctl restart ssh` |
| 磁盘满导致 sshd 无法写 | `df -h /` 100% | 先按 §6.4 腾空间 |
| 端口被改 | `ss -lntp` 只看到 2222 | 用 `ssh -p 2222 ...`；本地 `~/.ssh/config` 配 Port（§8.3） |
| 云厂商侧故障/实例异常 | 控制台监控无响应、VNC 也进不去 | 提交工单/控制台重启实例；先确认数据盘与快照 |

止血后**不要立即关掉当前会话**：先另开一个窗口验证能登录，再退出。

### 6.4 磁盘满

~~~bash
df -h /
df -i /                          # inode 满也会“写不进去”
du -xhd1 / | sort -h | tail -20
du -xhd1 /var/lib/docker /opt/fcmediaagent 2>/dev/null | sort -h | tail -20
lsof +L1 2>/dev/null | head -20
journalctl --disk-usage
~~~

处理优先级：

1. `logrotate -f /etc/logrotate.d/fcmediaagent`（日志是常见大头）。
2. 清理明确可删的旧备份/旧发布包（远端 `deploy-*` 解包目录、`dist.bak.*` 只留最近 2 份）。
3. `journalctl --vacuum-time=7d`（如果 journal 很大；注意本应用日志不在 journal）。
4. `docker image prune -f`；**绝不**执行 `docker system prune -a --volumes`（可能删掉 MySQL 数据卷/停止的容器）。
5. 找出被删除但仍占用的文件，重启对应进程释放。

腾出空间后立刻验证：MySQL 容器健康、API 健康、备份能跑、logrotate 正常。

### 6.5 worker 不心跳

见 §5.3。额外检查：

~~~bash
systemctl cat fcmediaagent-worker
grep -E 'FCM_EXECUTOR_MAX_STEPS|NODE_OPTIONS|WorkingDirectory|ExecStart' /etc/systemd/system/fcmediaagent-worker.service
tail -n 200 /opt/fcmediaagent/logs/worker.log
~~~

常见：`tool-loop.mjs`/`cloud-executor.mjs` 被覆盖成空文件/语法错误、`.env` 权限变化、数据库不可达、上游 hang 住、OOM。
若是刚发布后出现，直接按 §3.2 回滚 worker 文件。

### 6.6 nginx 502 / 504

~~~bash
curl -v --max-time 5 http://127.0.0.1:3000/api/health
systemctl status fcmediaagent-api --no-pager -l | tail -30
ss -lntp | grep ':3000'
nginx -t
tail -n 100 /var/log/nginx/error.log
systemctl status nginx --no-pager
~~~

判断：

- 本机 3000 正常、公网 502：nginx 配置/重载问题。`nginx -t` 通过后 `systemctl reload nginx`。
- 本机 3000 也失败：API 挂了，按 §5.1/§6.1 处理；502 只是结果。
- 504（超时）：长请求/SSE 被代理超时；确认 nginx 该站点已关闭 buffering，并检查 API 是否卡死。不要用无限加大超时掩盖 API 卡死。
- 刚重启 API 的几秒内出现 502 属正常，等健康检查通过再看。

## 7. admin 密码轮换

背景：admin 登录直接比对 `app/.env` 的 `ADMIN_USERNAME`/`ADMIN_PASSWORD`（无数据库哈希），所以**改 .env + 重启 API 即生效**，不需要改库。
初始密码是弱口令（见交接记录），必须轮换。JWT 默认 7 天有效，改密码**不会**让已签发的 admin token 立即失效；如需强制下线所有后台会话，需同时轮换 `JWT_SECRET`（会让所有用户重新登录，属高风险操作，需单独评估）。

~~~bash
cd /opt/fcmediaagent/app

# 1) 备份 .env（600）
~~~

## 8. SSH 加固 checklist

> 目标：仅密钥登录、限制来源 IP、fail2ban 兜底、端口不暴露在 22。
> **顺序不能乱**：先确认新方式可用，再关闭旧方式；全程保留一个已登录会话 + 阿里云 VNC。

### 8.0 前置

- [ ] 能通过阿里云控制台 VNC 登录（关键退路）。
- [ ] 本地 `~/.ssh/fcmediaagent_deploy` 私钥可用，`ssh -i ... root@47.85.46.165` 能登录。
- [ ] 已通知同事变更窗口；安全组可随时调整。
- [ ] 备份 sshd 配置：

~~~bash
TS=$(date +%Y%m%d-%H%M%S)
cp -a /etc/ssh/sshd_config "/etc/ssh/sshd_config.bak.$TS"
cp -a /etc/ssh/sshd_config.d "/root/sshd_config.d.bak.$TS" 2>/dev/null || true
echo "备份时间戳：$TS"
~~~

### 8.1 Checklist

- [ ] **1. 仅密钥登录**（先验证再关密码）
- [ ] **2. 禁止 root 密码登录**（`PermitRootLogin prohibit-password`）
- [ ] **3. 改 SSH 端口**（可选，建议 2222；先加新端口再删 22）
- [ ] **4. 安装并启用 fail2ban**
- [ ] **5. 安全组白名单**（SSH 仅办公/VPN IP；80/443 对公网；3000/3306 永不开放）
- [ ] **6. 验证并留档**
- [ ] **7. 更新本地 `~/.ssh/config`，保证发布脚本继续可用**

#### 8.1.1 仅密钥登录

Ubuntu 云镜像常在 `/etc/ssh/sshd_config.d/50-cloud-init.conf` 里写 `PasswordAuthentication yes`。sshd 对同一关键字**取第一个读到的值**，而主配置顶部 `Include /etc/ssh/sshd_config.d/*.conf` 按文件名排序加载，所以必须用排在 `50-` 之前的 **`00-hardening.conf`** 才能覆盖；写成 `99-` 反而无效：

~~~bash
cat <<'EOF' >/etc/ssh/sshd_config.d/00-hardening.conf
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin prohibit-password
EOF
chmod 600 /etc/ssh/sshd_config.d/00-hardening.conf
sshd -t
systemctl restart ssh
sshd -T | grep -Ei '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication)'
~~~

**验证**：新开一个终端用密钥登录成功；再试密码登录应被拒绝。确认后才能关闭当前会话。
若被锁：VNC 登录，`rm /etc/ssh/sshd_config.d/00-hardening.conf`，`systemctl restart ssh`。

#### 8.1.2 改 SSH 端口（可选）

~~~bash
# 1) 显式同时监听 22 与 2222（Ubuntu 默认 Port 22 是注释的，只加 2222 会直接失去 22）
grep -qE '^Port 22$' /etc/ssh/sshd_config || echo 'Port 22' >>/etc/ssh/sshd_config
grep -qE '^Port 2222$' /etc/ssh/sshd_config || echo 'Port 2222' >>/etc/ssh/sshd_config
sshd -t && systemctl restart ssh
ss -lntp | grep -E ':22|:2222'
~~~

2. 阿里云安全组**先放行 2222**（来源填你的固定 IP），再用 `ssh -p 2222 -i ~/.ssh/fcmediaagent_deploy root@47.85.46.165` 验证。
3. 确认 2222 可用后，再注释 22：

~~~bash
sed -i 's/^Port 22$/#Port 22/' /etc/ssh/sshd_config
sshd -t && systemctl restart ssh
ss -lntp | grep -E ':22|:2222'
~~~

4. 再开一个新会话验证 2222；稳定后再从安全组删除 22 的放行。
**注意**：`scripts/publish-update.mjs`、`scripts/publish-asar.mjs` 调 ssh 时没有 `-p` 参数。改端口后必须按 §8.3 配本地 `~/.ssh/config`，否则发布脚本会连不上。

#### 8.1.3 fail2ban

~~~bash
apt-get update
DEBIAN_FRONTEND=noninteractive apt-get install -y fail2ban

cat <<'EOF' >/etc/fail2ban/jail.local
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5
# 把办公固定 IP / VPN 出口加进来，避免自己把自己封了（示例 203.0.113.10，必须替换）
ignoreip = 127.0.0.1/8 203.0.113.10

[sshd]
enabled = true
port = 2222
backend = systemd
EOF

systemctl enable --now fail2ban
fail2ban-client status sshd
~~~

若端口仍是 22，把 `port = 2222` 改成 `port = 22`。查看封禁/解封：

~~~bash
fail2ban-client status sshd
# 把 203.0.113.10 换成 Banned IP list 里的实际地址
fail2ban-client set sshd unbanip 203.0.113.10
~~~

#### 8.1.4 安全组白名单

- SSH（22 或 2222）：只放行办公固定 IP / VPN 出口；不要 `0.0.0.0/0`。
- 80/443：对公网开放（业务需要）。
- 3000、3306、33060、2375/2376：**永不**对公网开放；本机验证 `ss -lntp` 只监听 127.0.0.1。
- 数据库端口如需外部管理，走 SSH 隧道，不要开安全组。

### 8.2 验证命令

~~~bash

sshd -T | grep -Ei '^(port|passwordauthentication|permitrootlogin|pubkeyauthentication)'
fail2ban-client status sshd
systemctl is-active ssh fail2ban
~~~

从本地验证：

~~~bash

~~~

### 8.3 改端口后更新本地 SSH config（必做）

编辑本地 `~/.ssh/config`（Windows 为 `C:/Users/30290/.ssh/config`），加：

~~~text

  HostName 47.85.46.165
  User root

  IdentityFile ~/.ssh/fcmediaagent_deploy
~~~

之后 `ssh 47.85.46.165`、`scp ... root@47.85.46.165:...` 以及 `publish-update.mjs` / `publish-asar.mjs` 都会自动走 2222。

### 8.4 回滚（被锁时）

VNC 登录后：



### 9.5 正式执行

1. 把脚本最后一行 `ROLLBACK;` 改为 `COMMIT;`。
2. 再次确认备份文件存在且 `sha256sum -c` 通过。
3. 执行，记录输出与时间。
4. 立即验证：


5. 用真实账号登录/发消息验证业务正常；观察 `api.log`/`worker.log` 5–10 分钟。
6. 把清单、SQL、备份文件名、执行时间写进交接记录。

### 9.6 失败处理

- 任何一步报 FK 约束错误：整段在一个事务里，`ROLLBACK` 已生效；不要逐条硬删，根据错误里的表名补删子表后再预演。
- 误删了真实用户：立即停 worker/API，按 §4.4 用最近备份恢复，并复盘白名单。
- 预演和正式执行之间数据可能变化（新任务/新订单）：正式执行前重跑一次盘点 SQL，确认 id 列表仍准确。
