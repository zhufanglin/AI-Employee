# P20 记忆自动去重/合并 + 多轮追问改写

上线：2026-11-08。前序：P18 长期记忆（增删查）、P19 记忆语义检索（扩展+重排）。

## 1. 为什么做

P18/P19 之后记忆能存也能查，但两个问题一直存在：

| 问题 | 具体表现 | 后果 |
| --- | --- | --- |
| 同一件事反复写 | 员工每完成一个任务就 `memory_save`，同一条偏好换个说法就成了新记录 | 检索结果一堆重复项，占满返回条数，老板还得自己判断哪条最新 |
| 追问查不到 | 「那她呢」「上面那个客户」只有代词，查询扩展和重排拿到的就是一个代词 | 追问必须把客户名再说一遍，否者检索为空 |

## 2. 设计取舍

- **查重不用编辑距离、也不用 embedding**：编辑距离对「半年付 / 半年一付 / 只做半年结算」无能；embedding 这条线 P19 已经证明当前账号没有（`doubao-embedding-*` 全部 404）。做法是把「新记忆 + 最多 6 条已有记忆」交给 `doubao-seed-2.0-mini`（关思考）判定三种关系：
  - `duplicate`：意思相同、无新事实 → 不新增，只累加 hitCount、合并标签；
  - `merge`：同一对象/主题但补充了新事实 → 让模型给出**合并后正文**写回原记录（保留 id 与 createdAt）；
  - `different` → 正常新增。
- **判定只是建议，永不丢记忆**：模型超时、JSON 坏、返回的 id 不在候选里、上游 500 —— 一律按新增写入。只有拿到合法 verdict 才改写已有记录。
- **候选来源两层**：先用 `splitTerms(content)` 做 LIKE 召回最近 6 条（能抓到同名词的）；字面完全改写时补最近 12 条（`DEDUPE_SUPPLEMENT_ROWS`），保证「赵姐只收季度付」能对上「赵姐 prefer 季度结账」。
- **追问改写放在能力层而不是执行器里写死**：`memory_search` 新增 `context` 参数；执行器 `recentContext()` 自动取最近 6 条 user/assistant 消息（每条截 300 字、合计 1200 字）塞进去，模型自己传了 `context` 就尊重模型的。这样任何调用方（云端执行器、桌面执行器、直接调 API）都能用，也便于单测。
- **性能**：改写、判定都复用 P19 的 mini + `thinking: { type: "disabled" }` + 8s 超时；改写结果按「context 末 240 字 + query」缓存 10 分钟。

## 3. 能力契约

### memory_save（新增参数 `dedupe`）

| 参数 | 说明 |
| --- | --- |
| content / title / tags / kind | 同 P18 |
| dedupe | `auto`（默认，先查重）\| `off`（直接新增，不调模型） |

返回新增 `action`：

| action | 含义 | 返回内容 |
| --- | --- | --- |
| `created` | 新记录 | id/kind/title/createdAt |
| `duplicate` | 命中同义记忆 | 原 id/kind/title/createdAt（tags 已合并、hitCount+1） |
| `merged` | 合并进原记忆 | 原 id + `content`（合并后全文） |

### memory_search（新增参数 `context`）

| 参数 | 说明 |
| --- | --- |
| context | 可选，最近几轮对话原文（≤1200 字）；普通追问由执行器自动带入 |

返回新增 `rewritten`（改写后的问题，未改写为 null）与 `effectiveQuery`（实际用于扩展/召回/重排的问题）。

### 环境开关

- `MEMORY_SEMANTIC=0`：关闭全部语义能力（扩展、重排、改写、查重），记忆退化为 P18 纯关键词行为；
- `MEMORY_SEMANTIC_MODEL`：覆盖判定/改写用的模型别名（默认 `doubao-seed-2.0-mini`）。

## 5. 验证

- 本地：`smoke-p20-memory.mjs` **47 项全绿**；全量 `scripts/verify.ps1 -Smoke`（需 `DATABASE_URL`）→ **VERIFY GREEN**。
- 生产（47.85.46.165，`/opt/node/bin/node prod-verify-p20.mjs`）：**13 项全绿**（`P20 PROD VERIFY GREEN (13 checks)`）；实测耗时：memory_save 新增 1.15–1.25s、查重 1.0–1.9s、合并 1.1–1.2s、带改写检索 3.0–4.5s。

| 场景 | 结果 |
| --- | --- |
| 存第一条（客户只做半年付/宁波港/45 天） | `created` 1.25s |
| 同义重写再存一次 | 不新增（`merged`/`duplicate`），复用原 id |
| 同一客户补充「12 月起账期改 60 天」 | `merged` 1.09s，原 id 不变 |
| 合并后检索同一条 | 正文同时包含「半年付」与「60天」 |
| 无关记忆 | `created` |
| `dedupe=off` | 允许写出第二条 |
| 追问「那她那边账期怎么改的？」+context | rewritten=`客户龙哥XXXX的账期是怎么修改的？`，命中该客户记忆 |
| 同一追问不带 context | rewritten=null（不瞎改） |
| 清理 | 三条测试记忆全部删除 |

> 说明：完全同义的两段文字，模型可能判 `duplicate` 也可能判 `merge`（把两种措辞合成一段）——产品要求是「不要写第二条」，生产脚本对两者都放行，`duplicate` 分支由本地单测（确定性假模型）覆盖。

## 6. 坑

1. **改写缓存按「context 末 240 字 + query」为 key**：单测里不同用例用同一段 context 会命中上一用例的缓存，导致「没有调用模型」的断言莫名失败 —— 测试前先 `clearRewriteCache()`。
2. **Prisma `updateMany` 的 where.id 是字符串**（不是 `{ in: [...] }`，P19 那次是 in），写通用 fake 要同时兼容两种形态。
3. **模型写合并正文时数字/单位不固定**：「60 天」「60天」都会出现，生产断言用 `/60\s*天/`，不要写死空格。
4. **查重候选只取当前用户最近记录**：生产验收必须用带时间戳的唯一客户名（`P20验收-<ts>`），否则会命中历史测试记忆，断言变得不可判定。
5. **memory_save 变慢是正常的**：一次查重多一次模型调用（约 1–2s），这是低频操作，不要为了省 1 秒把查重关掉。

## 7. 还没做

- 没有「批量清理历史重复记忆」工具（存量重复要手工 `memory_delete`）；
- merge 不保留版本历史（只留合并后的正文，createdAt 仍是首次写入时间）；
- 没做自动遗忘/降权（长期不用的记忆仍然参与召回）；
- 改写只处理记忆检索，其它能力（如 `content_query`）还没有追问上下文。
